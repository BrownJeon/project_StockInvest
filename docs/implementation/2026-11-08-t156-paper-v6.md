## 첫 웹 배포 시도 — 실패·자동 복구 이력

사용자가 즉시 웹 배포를 승인해 최신 main의 T-162 기록을 보존한 35파일 통합본을 게시했다. 별도 Ubuntu clone에 정상 훅을 설치했고 484개 훅 회귀·실커밋 scope 검사를 통과했다. 커밋 `319caf645e2bdd2b0babd18a4702682e2db135fe`의 제품19개 Git blob SHA는 검증본과 모두 일치한다. 원본 작업트리는 이 커밋으로 fast-forward했고, 이전 T-156 편집 사본은 이름 있는 복구 stash로 보존했다. 공통 Git 설정은 바꾸지 않았다.

자동 webhook은 2026-11-08 11:58:39 UTC에 시작했고 새 빌드·프로세스 기동 뒤 health 검사 제한을 통과하지 못했다. `RELEASE_RESULT status=health_failed`, 실패 릴리스 `20261108-205843-319caf64`, 12:02:32 UTC END exit1이며 자동으로 `20261108-174944-963bfeba`에 복구했다. 수동 중복 배포나 재시도는 실행하지 않았다.

복구 후 health200·DB 정상·safetygreen·DRY_RUNtrue/KILL_SWITCHfalse, web/cron 각1 online/restart0와 선택 안전 env 해시 불변을 확인했다. 실패 당시 새 웹 로그에 공시 캡처 DB 시간상한과 job-run-log timeout이 있었지만 원인은 확정하지 못했다. 이후 직접 DB ping12ms/유휴 연결은 실패 당시 잠금·풀 대기 부재를 증명하지 않는다. 쿼리 이력 수집이 꺼져 있어 당시 대기 관계는 복원되지 않았다. 격리 metadata lock 대기 실험은 자기참조 교착을 재현하지 못했다.

이번 UI 변경으로 원인을 확정하거나 ‘환경 문제’로 단정하지 않는다. 부팅 단계·DB 초기화·풀 대기를 구분하는 진단 보완 검토안을 `docs/implementation/2026-11-08-t156-paper-v6-deployment-followup.md`에 작성했다. 원인이 확인되기 전 동일 코드 재배포를 반복하지 않는다. 현재 main은319, 운영은963이므로 새 main push도 재배포를 유발할 수 있다는 점을 ACTIVE/RESUME에 표시했다. 배포 결과 증거는 artifacts의 deployment/에 보존한다. 신규 결과 문서는 로컬에 남기며 기록만을 위한 push도 하지 않는다.
