# T-156 v6 배포 실패 후속 검토안 (완료 이력)

작성 당시 조회UI는 구현·독립검토·388검사·타입/build·합성DB/화면 검증까지 완료했으나 운영 배포는 health timeout으로 자동 복구됐다. source/main 319caf6과 운영963bfeba를 구분한다. 실거래 차단은 유지된다.

## 확인한 사실과 확인할 수 없는 것

실패 릴리스 build는 통과했고 web/cron은 online/restart0이었다. health의 `ensureSetup()` 뒤 설정 조회가 완료되지 않은 정확한 지점은 기록되지 않는다. 실패 중 DB 시간상한 경고가 있으나 SQL/잠금 이력이 없어 원인을 특정할 수 없다. 새 reader의 열린 트랜잭션이 users DDL을 대기시킬 수 있음은 합성 재현했지만 자기참조 교착과 운영 당시 발생은 재현하지 못했다. 현재 정상 응답을 실패 당시 증거로 바꾸지 않는다.

## 제안 범위

| 단계 | 구체적 산출물 | 통과 기준 |
|---|---|---|
| 부팅 진단 설계 | ensureSetup 단계명·시작/완료/경과시간, 풀 연결 대기·쿼리 대기 구분, 제한된 운영 진단 기록 | SQL 값/키/계좌·보유·금액 노출 없음, 정상 주문/안전 동작 변경 없음 |
| 격리 재현 | 기존 스키마 부팅, 동시 조회, 잠금·지연 조건별 재현 | health 완료 지점과 지연 원인 구분, 연결/트랜잭션 정리, 외부/운영 DB 사용 없음 |
| 독립 검토와 영향 검사 | 실제 변경 파일의 Reviewer 판정, 부팅·보안·모의 주문 차단 회귀 | 새 오류 없음, DRY_RUN·권한·주문 경계 불변 |
| 통제된 운영 확인 | 별도 합의 범위의 진단 포함 릴리스와 동시 읽기 전용 대기 관측 | health 제한 내 통과, 정확한 SHA/프로세스·안전 상태 확인; 실패 시 자동 복구 결과 기록 |

이 안은 v6 화면 승인을 다시 받기 위한 것이 아니다. 전역 부팅/DB 초기화 경로까지 진단 코드의 범위를 넓힐지 검토하는 것이다. 원인 확인 전 설정 완화, health 검사 우회, DB 연결한도 상향, 수동 DDL·잠금 해제·프로세스 재시작·실거래 변경은 제안하지 않는다. 새 구현·진단 릴리스는 아직 실행하지 않았다.

최신 후속: 사용자가 이 진단 범위를 승인해 로그 관측만 구현·검토/208검사·실 mysql2호환 검증했고,39b2f749 진단 포함 릴리스가health를통과해운영반영됐다. 앞의319/main 대963/운영은이력이며현재는main/운영39다. 첫실패의근본원인은여전히미확정이다. 최신결과는paper-v6및boot-diagnostics구현보고서를따른다.
