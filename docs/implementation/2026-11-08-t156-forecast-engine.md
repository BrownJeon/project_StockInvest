## 저장과 사후 비교

`t156_forecast_job`은 실행 임대·진행 상태를 관리한다. `t156_forecast_run`, `t156_forecast_horizon`, `t156_forecast_evaluation`, `t156_forecast_continuation`은 INSERT 전용이며 DB 트리거로 UPDATE/DELETE를 거부한다. 4기간은 한 트랜잭션으로 발행한다. 입력·출처·원래 계좌 상태·정책·코드·시드·발행 시각·수수료·달력을 해시와 함께 동결하고 새 예측에는 새 ID를 부여한다.

조회 GET은 예측 생성·수집·DB 변경을 수행하지 않는다. 기존 소유자 권한을 비공개 데이터 조회보다 먼저 검사하고 private/no-store 응답을 유지한다. 원본 선택과 10행 페이지를 지원하며, 새 예측이 들어와도 선택한 원본을 소급 교체하지 않는다.

만기가 오기 전에는 실제 손익을 만들지 않는다. 만기 후에는 같은 계좌·정책·교체 기준·기간과 연속된 모의 실행 증거, 수량·현금흐름·주식분할 기준·수수료가 맞을 때만 실제 순손익·예측 평균 대비 오차·범위 포함 여부·Brier 점수를 추가한다. 누락은 미확인, 조건 변경은 비교 불가로 구분한다. 평가는 원본을 수정하지 않고 새 기록으로 남긴다.

기존 모의투자 커밋 뒤 최대 1.5초의 별도 연속성 기록을 추가한다. 이 기록의 실패는 기존 모의투자 성공을 취소하지 않는다. 증거가 없으면 사후 비교가 완료로 통과하지 않는다. 판단·주문·실매매 정책은 변경하지 않는다.

## 운영 적용 사전 계획

1. 독립 Reviewer와 수치 Analyst 검토, 정확한 소스 해시를 고정한 격리 QA를 통과시킨다.
2. 운영 DRY_RUN·계좌/모의 이력·안전 설정의 해시와 신규 표 부재를 확인한다. 원문 금융정보·비밀은 출력하거나 Git에 넣지 않는다.
3. 승인된 신규 5개 표와 불변 트리거만 명시적으로 적용한다. 기존 동명 트리거가 있으면 적용 전 정의를 검증하고, 적용 후 8개 정의를 전부 재검증한다. 부팅 초기화에 DDL을 추가하지 않는다.
4. 정상 훅·독립 감사 범위를 충족한 커밋을 운영 ref로 게시하고, 자동 blue/green 배포 한 번만 수행한다. 새 forecast cron은 기존 별도 작업으로 10:00 KST에 하루 한 번 호출되며 기존 08:40 모의 실행 일정은 유지한다.
5. 검증된 운영 릴리스의 인증된 forecast 작업으로 실제 원본 예측 1건·4기간을 발행한다. 원본 모의계좌/시그널/안전 설정 해시 불변과 중복 발행 방지를 확인한다. 인증키는 프로세스 메모리에서만 전달한다.
6. 실제 릴리스 SHA/파일 해시·health·단일 web/cron·DRY_RUN·비공개 API 권한과 원장 읽기를 확인한다. 실제 로그인 화면·안드로이드 실기기 확인 여부를 별도로 표시한다.

복구는 기존 코드 릴리스로 되돌려 새 작업을 중지하는 방식이다. 이미 발행된 예측 원장과 신규 표는 보존한다. 운영 기존 표의 삭제·초기화·실계좌 변경이나 실거래 활성화를 수행하지 않는다. 실패가 있으면 수정 후 Reviewer부터 다시 검증하며 배포 상태 검사를 완화하지 않는다.

## 운영 DDL 권한 중단 — 2026-11-08 23:15 KST

검토된 SQL SHA `163ce1df773754b5a331944be14eedcd357310ba19ae03d5f3bf5078aa67753b`를 운영 `stockinvest` DB에 명시 적용했다. CREATE/TRIGGER 권한 사전 점검은 통과했지만, 실제 서버의 `log_bin=1`, `log_bin_trust_function_creators=0`, `binlog_format=ROW` 조건에서 첫 CREATE TRIGGER가 `ER_BINLOG_CREATE_ROUTINE_NEED_SUPER`(1419)로 거부됐다. [MariaDB 공식 설명](https://mariadb.com/docs/server/reference/error-codes/mariadb-error-codes-1400-to-1499/e1419)에 따르면 이 조건은 별도 관리자 권한이 필요하다. 격리 DB의 DDL 통과가 운영의 이 추가 권한을 검증한 것은 아니었다.

현재 신규 job/run/horizon/evaluation 4표는 전부 0행이고, continuation 표와 보호 트리거 8개는 없다. 기존 모의계좌 1행·회차 1행·시그널 4행·안전 설정의 적용 전후 해시는 동일하다. 운영 릴리스는 기존 `39b2f749`를 유지한다. 새 원본 예측·새 cron·새 코드 게시/배포는 하지 않았다.

23:19 KST 후확인: health200/DBtrue/schemaFatalfalse/safetygreen/DRY_RUNtrue/KILL_SWITCHfalse, web·cron 각각 1개 online/restart0, 익명 비공개 API401. 실제 운영의 핵심 3파일은 기존39 Git 객체와 동일했다. 공통 배포 절차서의 오래된 ‘선결조건 미해소’ 표와 현 상태를 구분한다. 실제 실행은 릴리스 디렉터리, 기존 단일 web/cron, 기존 release webhook 방식, 공용 의존성 링크, `.env`600으로 확인했고 사용자의 기존 즉시 웹 배포 승인은 유효하다. 이번 새 배포를 막는 실제 사유는 DB 관리자 트리거 권한이다.

전역 신뢰 설정 완화, 앱 계정의 SUPER 승격, 트리거 없는 발행으로 우회하지 않았다. 현재 앱 환경과 프로젝트 절차에서 실제 사용 가능한 관리자 프로필을 확인하지 못해 사용자에게 기존 DB 관리자 접속 프로필 경로 또는 관리자 직접 적용을 요청했다. 비밀번호·키를 대화로 요청하지 않는다. 추천은 관리자 계정으로 검토된 SQL만 1회 적용하고 전역 보안·앱 권한을 유지하는 것이다. 상세 인계는 `docs/implementation/2026-11-08-t156-forecast-dba-handoff.md`.

관리자 적용 후에는 동일 SQL의 멱등 재실행, 정확한 8개 트리거 정의와 신규 5표 확인, 기존 자료/설정 불변 확인을 먼저 한다. 그다음 정상 훅 커밋·운영 ref 게시·단일 자동 배포·실자료 첫 발행 및 중복 방지 검증을 진행한다. 운영에 빈 신규 표를 삭제하거나 기존 자료를 롤백하지 않는다.

추가 운영 한계: 현재 공식 달력 범위는 2027-12-31까지다. 현재 4기간은 범위 안이지만, 향후 목표·결제일이 범위를 벗어나면 계산을 차단한다. 다음 연도 공식 달력 확장이 필요하다. 이는 날짜를 임의 생성해 보완하지 않는다.
