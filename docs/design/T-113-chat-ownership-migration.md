# T-113 대화 소유권 — 스키마 및 이력 이관 초안

> **2026-11-06 보관 안내** — T-113 운영 이관은 이 문서의 다중 사용자 전제 절차(접근 차단·drain 등)가 아니라 **단일 사용자 대안 순서**(재측정 → 암호화 백업·격리 복원 → DDL → 배포 → 가드 백필)로 완료됐다(릴리스 `20261106-231601-c33e4678`, 근거 `agent-vault/10-Flow/tasks/T-113-chat-ownership-authorization.md` 「운영 이관 실행」·「운영 이관 완료」). 이 문서와 관련 도구는 그 이관에 쓰이지 않았으며 다중 사용자 상황 대비 보관용이다. 재사용 전 현재 스키마(`user_id` 이미 존재)·사용자 수 기준으로 재검토할 것.

> 상태: 격리 개발·검토용. 이 문서 작성자가 운영 MariaDB 조회·DDL·백필을 실행한 기록은 없다. 별도 담당자가 아래 시점의 운영 집계를 읽기 전용으로 보고했다. `scripts/migrations/T-113-chat-ownership.sql`은 검토 대상이며 적용은 기존 프로젝트의 운영 DDL 승인·배포 절차를 따른다. [기존 다중 사용자 설계](../superpowers/specs/2026-08-04-multi-user-kis-accounts-design.md)

## 결정과 이력

- 기존 승인 설계(2026-08-04)는 `chat_threads`와 `chat_messages` 각각에 `user_id INT UNSIGNED NOT NULL`을 추가하고 기존 행을 첫 가입자에게 귀속하도록 명시했다. 당시 승인 사실을 유보하거나 삭제하지 않는다.
- 별도 담당자 보고에 따르면 2026-11-04 22:28 KST 운영 읽기 전용 집계는 사용자 1명·스레드 13개·메시지 32개이며 `chat_threads` owner 열은 없고 현존 사용자의 최소 생성 시각은 유일하다. 이는 **해당 시점의 집계**이며 현재 값이나 사용자 신원을 이 문서 작성자가 직접 재확인한 것은 아니다. 이후 사용자가 **“현재 계정이 기존 대화의 소유자이고 삭제된 이전 계정이 없습니다”**라고 명시했다. 이는 기존 귀속 결정과 부합하는 사용자 확인이다. 운영 실행 시 이 확인을 실제 단일 사용자 ID와 안전하게 연결하고 현재 상태·대상 집합을 다시 검증해야 한다. 구체적인 운영 이관은 앱 구현이나 QA 통과만으로 실행하지 않는다.
- 이번 구현 제안은 **안전한 중간 단계**다. `chat_threads.user_id`만 nullable로 추가하고 미분류 이력은 NULL 그대로 보존한다. `chat_messages` 소유권은 부모 스레드의 사용자 ID를 통해 검사한다. 이는 원안의 양 테이블 NOT NULL 최종 구조 및 백필을 이미 이행했다는 뜻이 아니며, 단일 소유자 정본 방식의 차이는 독립 리뷰와 프로젝트 결정 기록에 남겨야 한다. 원안의 기존 데이터 귀속 승인 자체를 철회하거나 사용자 재승인을 자동으로 요구하는 것은 아니다.

## 대상과 요구 계약

| 항목 | 제안 |
|---|---|
| owner 열 | `chat_threads.user_id INT UNSIGNED NULL DEFAULT NULL`, `users.id`와 정수·unsigned 형태 일치. 새로운 이력은 서버가 검증된 세션에서 얻은 사용자 ID를 기록한다. 클라이언트의 user ID는 신뢰하지 않는다. |
| 인덱스 | `idx_chat_threads_user_archived_updated (user_id, archived, updated_at)`; 실제 질의·실행 계획은 격리 DB에서 확인 필요. |
| 메시지 | `chat_messages.thread_id`의 소유 스레드에 연결해서 소유권을 검사한다. 별도 `chat_messages.user_id`를 생성·수정하지 않는다. 메시지 직접 접근 경로가 단 한 곳이라도 이 부모 검사를 건너뛰면 차단 조건 불충족. |
| 기존 행 | `user_id IS NULL`: 소유자 미분류. 어느 사용자에게도 자동 공개·귀속·삭제하지 않는다. 기존 메시지·ID·시각·카운트는 그대로 보존한다. |
| FK | `chat_threads.user_id`의 users FK는 이번 ALTER에 포함하지 않는다. 첫 설치 시 `chat_threads`가 `users`보다 먼저 생성되고, 계정 삭제 시 이력 보존 정책 및 레거시 귀속이 미결정이기 때문이다. 앱의 인증 사용자 유효성·삭제 사용자 세션 처리와 고아 owner 탐지는 별도 필수 검증이다. |
| 사용자 확인 | 기존 `requireUserId`는 세션 서명/만료를 검증하지만 users 행 존재 자체는 보장하지 않는다. 삭제·비활성 계정 처리 정책과 존재 검사/세션 폐기를 API 담당자가 구체적으로 검증해야 한다. |
| 새 빈 DB | `src/lib/db.ts`의 `CREATE TABLE IF NOT EXISTS chat_threads`에 같은 열·인덱스를 명시한다. 이 문장은 표가 아예 없을 때만 새 정의로 생성하며 기존 표의 ALTER·백필을 실행하지 않는다. 기존 DB는 수동 마이그레이션이 필요하다. |
| 스키마 부재 | 새 서버 코드는 소유자 열이 없거나 DB가 실패하면 에러를 반환하고 기존 무스코프 경로로 되돌아가지 않는다. 정확한 응답 형식은 API 계약의 범위다. |

### 8월 승인 명세와의 차이 및 미결

| | 8월 승인 명세 | 이번 중간 단계 제안 |
|---|---|---|
| 대화 소유자 | `chat_threads.user_id NOT NULL` | `chat_threads.user_id NULL` 허용, 신규 대화는 인증 사용자 기록 |
| 메시지 소유자 | `chat_messages.user_id NOT NULL` | 메시지에 새 열 없이 부모 스레드의 `user_id`를 단일 정본으로 조회 |
| 기존 행 | 두 테이블의 기존 행을 첫 가입자에 일괄 귀속 | 기존 행을 NULL 소유 스레드 아래 보존·비노출. 검증된 후속 이관은 별도로 계획 |

부모 단일 정본은 메시지와 스레드의 소유자 값이 서로 달라지는 중복을 피하고 현재 `thread_id`/외래키 구조를 이용한다. 반면 메시지만 직접 조회하는 모든 소비자는 반드시 부모와 연결해 인가해야 하고, 스레드 소유자 변경이 과거 메시지 전체의 접근권 변경으로 이어진다. 소유자 이전·공유 대화·관리자 접근 정책, 변경 이력과 감사는 아직 설계하지 않았다. 중복 `user_id` 방식은 메시지만 조회할 때 필터를 직접 적용할 수 있지만 스레드와 메시지 간 소유권 일치 제약·동시성 검증이 추가로 필요하다. 어느 방식이 전체 프로젝트 의존 쿼리에 더 적합한지와 최종 스키마는 이 제안만으로 확정되지 않는다.

현재 로컬 `src/`·`scripts/`의 `chat_threads`/`chat_messages` 문자열 검색에서는 채팅 API·`db.ts` 외 소비자를 찾지 못했다(개발 중인 API와 본 마이그레이션 파일 포함, 2026-11-04 정적 검색). 이는 동적 SQL, 다른 저장소·운영 잡·과거/미커밋 변경의 부재를 입증하지 않는다. 새 API가 소유자 부모 JOIN·원자적 쓰기를 실제로 구현하고 모든 경로가 적용되는지는 독립 리뷰·테스트의 별도 판정 대상이다. **이 제안은 8월 승인 명세와 다르며**, 최종 채택 전 명세와 이행 계획에 차이를 명시하고 프로젝트 결정 절차를 거친다. 과거 사용자 승인을 철회하거나 소급 변경하지 않는다.

## SQL 파일 및 재실행

`T-113-chat-ownership.sql`은 세션 `lock_wait_timeout = 5`와 **열·복합 인덱스 추가를 담은 단일 ALTER** 외에는 실행 문장이 없다. UPDATE·INSERT·DELETE·DROP·소유권 귀속이 없다. 5초 설정이 모든 종류의 쿼리·작업 전체를 5초로 제한한다는 뜻은 아니다.

- **자동 멱등 아님.** 동일 열 또는 인덱스가 있으면 중단하고 `SHOW CREATE TABLE` 및 `information_schema`에서 열 타입·NULL 허용·기본값, 인덱스 열 순서·이름과 실제 ALTER 결과를 점검한다. `IF NOT EXISTS`는 서로 다른 정의를 성공처럼 숨길 수 있어 사용하지 않는다.
- DDL은 암묵적 commit과 메타데이터 잠금이 수반될 수 있다. 트랜잭션·코드 롤백이 DDL을 취소한다고 가정하지 않는다. MariaDB 10.11의 실제 작업 방식과 소요 시간은 격리 환경에서 확인해야 한다.
- 실행 도중 timeout, 연결 단절, 재시작 등 결과가 불명확하면 자동 재시도하지 않는다. 앱 접근을 제한한 채 스키마·인덱스와 사용자/대화 row counts, 데이터 백업 및 인가 상태를 조사한다. 열만 있거나 인덱스만 있는 등 예상과 다른 상태도 자동으로 수리하거나 소유자를 채우지 않고 독립 검토 후 복구 계획을 정한다.
- 자동 부팅 `setupDB()`에 기존 테이블 ALTER를 넣지 않는다. 개발·운영이 DB를 공유할 수 있으므로 테스트는 운영 풀을 사용하지 않는다.

## 구버전 공존과 적용 순서 — 배포 전 필수 구체화

**중요: DB에 소유자 열만 추가해도 기존 무인가 코드가 해당 열을 무시해 모든 대화를 조회·수정할 수 있다.** 구버전과 신버전의 동시 기동·롤백은 사용자 격리를 깨뜨릴 수 있다. 기존 앱에 이 변경을 넣었다고 이미 안전하거나 메뉴 공개가 가능하다고 간주하지 않는다.

1. 실데이터 변화를 피할 수 있는 범위에서 현재 배포·접근 경로와 모든 앱 인스턴스, 쓰기 작업·장기 LLM 요청·내역 백업과 복원 가능성을 확인한다. 비상 접근 차단 및 기존 병행 작업을 반영한 전환 창과 담당자를 정한다.
2. 사용자별 서버 인가 코드와 테스트, 신규 DB 생성 경로, 마이그레이션을 독립된 일회용 MariaDB에서 검증한다. 현행 보호 경계와 구버전 차단 방법을 먼저 확정한다.
3. 기존 작업 규정에 따른 운영 DDL 승인과 전환 계획이 성립하면 접근을 적절히 차단하고 이전 앱/장기 요청의 종료를 확인한 후 수동 DDL을 적용한다. 실제 수행·서버 재시작·설정 변경을 이 문서가 허가하지 않는다.
4. 새 코드가 모든 경로에서 fail-closed이고 schema 정의가 일치하는지 확인한 뒤에만 접근 재개를 판단한다. 이력은 소유자 미분류로 남으므로 사용자는 기존 이력을 즉시 보지 못할 수 있다. 추가적인 데이터 귀속은 기존 승인된 정책의 적용 근거, 첫 가입자 식별 및 실제 데이터 범위·동시 사용자 상황을 조사한 후 별도 작업 계획에 따른다.
5. 코드 장애 시 구버전으로 단순 복귀하면 사용자 간 데이터 노출이 가능하다. **사용자 접근이 차단된 상태**에서만 복원 대안을 검토하고, 소유자 열은 유지·백업을 보존한다. 소유자 열/인덱스 제거와 데이터 삭제는 이 파일이나 자동 롤백에 없다. 구버전 경로·API 차단 여부를 확인하기 전에는 안전한 사용자 서비스 롤백이 검증된 것으로 보지 않는다.

## 기존 이력 백필 — 검토 가능한 계획, 미실행

별도 [백필 계획 파일](../../scripts/migrations/T-113-chat-ownership-backfill-plan.sql)은 **모든 줄이 주석**인 비실행 SQL 예시다. 운영 수치를 끼워 넣거나 주석을 제거해 바로 실행하는 런북이 아니다. 8월 결정의 첫 가입자 귀속은 유효한 과거 의사결정으로 보존하며, 계획은 그 결정을 철회하거나 새로운 승인을 자동으로 요구하지 않는다. 다만 이번 단일 부모 정본·NULL 중간 단계는 당시의 양 테이블 NOT NULL 명세와 다르므로 최종 스키마 차이와 실제 이관 절차의 프로젝트 판단이 필요하다.

1. **대상과 권한 확정:** 사용자의 기존 확인을 존중하고, 실행 직전 현존 `users`가 정확히 1개인지, 그 계정이 사용자가 확인한 계정과 같은지 권한 있는 운영자가 비공개 방식으로 연결·검증한다. 원문의 소유권 확인을 다시 묻지 않는다. 보관된 대화도 포함해 이관 대상은 소유자 NULL인 기존 대화의 정확한 집합이다. 별도 계정·소유자가 새로 발견되거나 대상에 모순이 있으면 그 새 사실만 구분하여 판단한다. 숫자 ID·계정 정보는 공유 보고서에 기록하지 않는다.
2. **전환 준비:** 대상 스키마·인덱스·부모 메시지 FK를 확인하고 사용자/스레드/메시지 및 정확한 영향 행의 접근 통제된 백업·복원 가능성을 검증한다. 영향 스레드 ID, 기존 `user_id`·`updated_at`, 보관 여부, 메시지 수를 보호된 검증 자료에 저장한다. 실제 개인정보·질문 내용·계정 식별자는 작업 보고서나 로그에 남기지 않는다. 영향 행 집합이 명확하지 않으면 중단한다.
3. **접근 격리와 DDL:** 구버전 API가 owner 필터를 무시하므로 구/신 버전이 사용자에게 동시에 노출되지 않도록 하고, 쓰기 경로 및 장시간 LLM 요청을 비운다. 금융 서비스는 별도 허용되지 않은 중단·재시작을 하지 않도록 정확한 경로별 차단 계획을 수립한다. 운영 DDL은 프로젝트 규정상 사용자 명시 승인이 필요한 별도 실행이며 QA PASS가 대체하지 않는다. DDL 후 스키마 결과가 불확실하면 접근을 막은 상태에서 조사하고 자동 재시도하지 않는다.
4. **백필과 검증:** 운영 DDL 승인과 별개로 귀속 DML이 현재 사용자 지시·기존 승인에 포함되는지 실행 주체가 확인한다. 백업한 정확한 대상 행만 잠그고 NULL 소유자에 한해 사용자가 확인한 현재 계정을 지정하는 계획이다. `updated_at`은 자동 갱신 열이므로 기존 값의 명시적 유지·비교가 필요하다. 실제 SQL의 실행 권한·동시성 제어·정확한 변경 전후 행 집합 일치는 아직 미검증이다. 기존 소유자 있는 행·새 사용자 데이터는 덮어쓰지 않는다. COMMIT 전 대상 ID·영향 건수·소유권·메시지 수·보관 여부·시각을 대조하고 불일치 시 ROLLBACK; COMMIT 결과 불명 시 접근을 계속 차단하고 재시도 전에 조사한다.
5. **접근 재개·복원:** 해당 사용자만 기존 이력에 접근하고 다른 사용자는 조회·변경·삭제·LLM 호출을 할 수 없는지 확인한다. 구버전 코드로의 단순 롤백은 무스코프 접근을 복원할 수 있어 사용자 접근 차단 없이 허용하지 않는다. 복원이 필요하면 백업된 정확한 영향 행의 소유자·시각만 전환 이후 변경 여부를 검증한 뒤 복원하고, 뒤에 생긴 데이터를 덮는 전체 DB 복원이나 전 행 NULL 처리를 하지 않는다. 복원 후에도 안전한 serving 코드와 인가가 검증될 때까지 접근을 제한한다.

**검증 상태:** 별도 QA에서 격리 MariaDB의 T-113 소유권 DDL/인가 관련 시험이 통과했다고 전달받았다. 이는 **운영 백필 절차 전체·실제 데이터 귀속·백업 복원·구/신 앱 전환**이 시험되었다는 뜻이 아니다. `updated_at=updated_at` 표현식과 임시 STOP 하네스만 아래 격리 범위에서 확인했다. 계획의 임시 테이블 JOIN 및 `t.updated_at = scoped.previous_updated_at` 구문은 실행 검증하지 않았다. 백필 시나리오는 영향 행, 동시 쓰기, 중단·재실행, 롤백과 기존 이력 보존을 포함해 일회용 DB에서 별도 시험하고 독립 검토해야 한다. 결과·정확한 시험 범위는 T-113 작업 이력서가 정본이다.

## 격리 검증 및 미확인

- 신규 빈 DB에서 setup 정의가 적용될 때 열·인덱스가 동일한지; 기존 DB ALTER 전에는 새 API가 fail-closed인지, 후에는 NULL 소유 이력이 계속 보존·비노출되는지.
- 다른 회원의 목록·상세·삭제·수정·초안·메시지 생성 및 LLM 입력 전에 소유권을 차단하는지, 직후 삭제/소유권 변경 경합에서도 타인 쓰기·정보 노출이 없는지.
- DDL을 두 번 호출하면 두 번째 실패 여부와 기존 정의/데이터 유지, 이미 부분 적용·잘못된 타입/인덱스/결과 불명, NULL legacy·고아 owner, 잠금 timeout, 백업·복원 시나리오.
- 별도 담당자의 위 시점 운영 집계 외에 이 문서 작성자는 실제 DB·스키마·행을 조회하지 않았다. 일회용 MariaDB의 기존 QA 결과는 T-113 작업 기록의 범위로만 인정한다. 이 백필 계획의 SQL 실행·DDL 잠금·재실행·복구는 검증하지 않았다. 사용자의 소유권 확인은 받았으나 이를 현재 DB의 단일 사용자 ID와 연결하는 운영자 검증, old/new 배포 동시성·사용자 접근 차단 방식·소요 시간은 미확인이다.

## 격리 검증 결과 (2026-11-04)

- 가상 사용자·기존 대화·메시지를 넣은 네트워크 차단 일회용 MariaDB 10.11.11에서 owner 열 추가·기존 행 보존·재실행 오류, 실제 서명 세션과 SQL을 이용한 두 사용자 격리 및 일부 저장 실패 롤백을 확인했다. 라우트 통합 8/8, 모의 라우트·스키마 계약 24/24, 타입검사 exit 0. 실제 서비스 검증은 아니다.
- 별도 합성 fixture 18개 assertion으로 NULL 행 한정 owner 설정, `updated_at=updated_at`의 기존 시각 보존과 transaction rollback을 확인했다. 불일치 시 STOP은 QA 임시 하네스가 수행했으며, **주석 전용 백필 계획에는 자동 STOP 실행 로직이 없다.** READ COMMITTED 한 예시에서는 대상 행 잠금 중 다른 연결의 새로운 NULL 대화 삽입이 가능했다. 따라서 대상 행 잠금만으로 쓰기 중단을 보장할 수 없다.
- 소유자에 대한 사용자 확인은 받았으며 이를 실행 시점 DB 계정에 연결하는 독립 검증, 백업과 복원, 모든 격리 수준, 운영 전환·구버전 접근 차단은 여전히 미검증이다. QA 상세는 `agent-vault/10-Flow/tasks/T-113-chat-ownership-authorization.md`의 QA 기록 참조.
