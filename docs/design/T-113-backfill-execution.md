# T-113 소유권 이관 실행안 (검토용)

> **2026-11-06 보관 안내** — T-113 운영 이관은 이 문서의 다중 사용자 전제 절차(접근 차단·drain 등)가 아니라 **단일 사용자 대안 순서**(재측정 → 암호화 백업·격리 복원 → DDL → 배포 → 가드 백필)로 완료됐다(릴리스 `20261106-231601-c33e4678`, 근거 `agent-vault/10-Flow/tasks/T-113-chat-ownership-authorization.md` 「운영 이관 실행」·「운영 이관 완료」). 이 문서와 관련 도구는 그 이관에 쓰이지 않았으며 다중 사용자 상황 대비 보관용이다. 재사용 전 현재 스키마(`user_id` 이미 존재)·사용자 수 기준으로 재검토할 것.

**상태: 운영 실행 불가.** 아래는 운영 전 준비와 검증 절차이며, 운영 DB에는 적용하지 않았다. 별도 fixture 전용 프로그램과 함께 제공된 운영 도구 연구용 초안은 기본 비활성 상태이지만, 환경변수 및 설정을 제공하면 임의 서버에 TLS 연결하고 실제 UPDATE·COMMIT을 실행할 수 있다. 그 기능이 구현되었다는 사실은 운영 사용이 안전하거나 승인되었다는 뜻이 아니다. 테스트에는 운영 자격증명·네트워크를 제공하지 않는 격리 프로세스와 합성 데이터만 사용한다. 실제 적용 전 독립 감사·복원 리허설, 운영 승인 및 접근 차단 증거가 필요하다.

## 이관 대상과 전제

사용자는 현재 계정이 기존 대화 13개의 소유자이며 삭제된 이전 계정이 없다고 확인했다. 과거에 측정된 사용자 1명, 대화 13개, 메시지 32개는 시점에 따라 바뀔 수 있으므로 작업 직전 다시 측정한다. 확인된 계정의 실제 식별자는 보호된 채널에서 별도 확인하고 DB의 유일한 계정과 정확히 대조한다. 식별자나 대화 내용은 결과 로그에 기록하지 않는다. 차이가 있거나 단일 계정임을 확인하지 못하면 중단한다.

범위는 `chat_threads`의 기존 소유자 미지정 대화 전체다. 메시지는 부모 대화에 귀속되는 기존 관계를 검증하며 직접 변경하지 않는다. 보관 대화도 포함한다. 이미 소유자가 설정된 대화, 예상 밖 계정·대화, 고아 메시지, 스키마 차이 또는 별도 작성자가 발견되면 판단 없이 중단한다. 원래의 migration 문서와 스키마를 작업 당일 대조한다.

## 운영 전환 순서

1. **접근과 작성 차단:** 채팅을 사용하는 모든 진입점과 구·신 버전 인스턴스, 직접 포트 접근, 배치·재시도·관리자·DB 직접 작성 경로를 식별하고 외부 차단한다. 예전 점검의 직접 포트 노출 여부는 현재 상태의 증거가 아니다. 실제 네트워크 규칙과 각 경로의 차단을 독립적으로 검증한다. 매매 기능은 영향 범위를 확인해 유지한다. 차단을 이 도구가 보장하지 않는다.
2. **진행 중 요청 정리:** 새 요청이 차단된 이후 모든 인스턴스의 채팅 요청, 스트림, 큐 및 재시도를 관찰해 완료 또는 안전한 중단을 확인한다. 고정 시간 대기만으로 완료를 판정하지 않는다. 추가 사용자 생성과 DB 작성도 차단한다. 확인할 수 없으면 중단한다.
3. **백업·복원 검증:** 차단된 시점의 일관된 백업을 보호된 저장소에 남기고 무결성·복원 지점을 기록한다. 격리된 DB에 복원해 스키마, 행 수, 모든 대화·메시지의 내용과 관계, 관련 스키마 및 행 수를 전수 대조한다. 백업 성공만으로 복원 가능하다고 판단하지 않는다. 실제 백업과 복원 실습은 아직 하지 않았다.
4. **변경 전 재측정:** 보호된 manifest에 대화 ID 전체, 보관 상태, 원래 `updated_at`, 메시지 ID와 부모 관계 및 건수를 기록한다. 변경 전 `user_id` 컬럼이 없으면 부재를 스키마 상태로 기록하고, DDL 이후 모든 기존 대상의 값이 NULL인지 검증한다. 이미 컬럼이 존재하면 변경을 중단하고 상태를 조사한다. 암호화·접근 제한된 곳에 저장하고 공개 로그에는 건수·무작위 실행 식별자 및 검증 결과만 남긴다. 이중 확인한 owner와 작업 대상 DB의 서버·DB 식별을 검증하고 최소 권한의 일회성 계정으로 진행한다. 입력은 대화형 또는 보호된 파일을 사용하며 명령줄 인수·로그에 비밀을 넣지 않는다.
5. **스키마 변경:** 기존의 승인된 설계에 따라, 실제 스키마를 검증한 뒤 필요한 컬럼·인덱스 DDL을 별도의 승인된 실행에서 적용한다. 예시 형식은 `ALTER TABLE chat_threads ADD COLUMN user_id INT UNSIGNED NULL DEFAULT NULL, ADD INDEX idx_chat_threads_user_archived_updated (user_id, archived, updated_at)`이며 실제 버전·현재 인덱스와 일치하는지 사전 검증해야 한다. MariaDB DDL은 묵시적 커밋 경계가 있으므로 백필 트랜잭션에 포함해 롤백할 수 있다고 가정하지 않는다. 성공 여부가 불명확하면 재실행하지 않고 스키마를 먼저 확인한다.
6. **백필 설계:** 하나의 DB 연결에서 `BEGIN` 후 사용자·대상 대화 및 필요한 관계를 잠그고, 보호된 manifest의 정확한 집합과 소유자·수정 시각·메시지 관계 및 행 수를 다시 비교한다. 단일 계정 조건과 미지정 행의 전체 집합도 다시 비교한다. 불일치 시 `ROLLBACK`. 검증된 ID 집합과 `user_id IS NULL`을 조건으로 업데이트하고 `updated_at = updated_at`으로 기존 시각을 보존하는 방식을 실제 스키마·트리거에서 검증한다. 영향 행 수와 전체 집합, 기존 소유 대화·메시지 불변성을 같은 트랜잭션에서 검증한 뒤에만 `COMMIT`한다. 제약 위반이나 검증 오류는 `ROLLBACK`한다. 이는 의사 절차이며 아직 운영용 코드가 아니다.
7. **완료 확인 및 재개:** 커밋 결과를 명확히 확인하고, 차단을 유지한 채 새 연결에서 전체 소유권과 대화·메시지 수, 기존 시각과 앱 인가를 검증한다. 결과 불명 또는 연결 단절 시 자동 재시도하지 않는다. 재접속 후 현재 데이터와 manifest를 대조해 커밋·미커밋을 판별하고, 판단 불가면 차단을 유지한다. 인가 적용 및 회귀 검증을 마친 후 단계적으로 접근을 재개한다. 이전 무인가 코드를 접근 가능한 상태로 되돌리지 않는다.

**잠금 한계:** `FOR UPDATE`는 시작 전에 같은 연결에서 트랜잭션이 있어야 한다. 또한 격리 수준과 접근 경로에 따라 새 미지정 행 삽입을 막는다는 보장은 없다. 외부 작성 차단, 실행 전후 집합 비교 및 드리프트 검출은 필수이며 어느 하나가 불확실해도 진행하지 않는다. 복구는 기존 백업으로 영향 범위를 판단한 후 수행한다. 부분 업데이트를 무조건 역적용하거나 이후 정상 작성된 데이터를 덮어쓰지 않는다.

## 격리 프로토타입 및 남은 일

`scripts/migrations/T-113-chat-ownership-backfill.mjs`는 `--fixture-only` 외 실행을 거부하고, 정해진 로컬 소켓 형식, networking 비활성, 합성 서버·DB·계정과 고정된 두 대화 및 두 메시지의 정확한 상태를 요구한다. 테스트 데이터에서만 트랜잭션, 오류 롤백 및 시간 보존을 실험한다. 이 조건은 합성 환경용 보호 장치이지 운영 DB 식별이나 외부 작성 차단의 증명이 아니다. 이 fixture 전용 프로그램에는 운영 입력과 전환 통제가 없다.

### 운영 도구 연구용 초안 (실행 금지)

`scripts/migrations/T-113-chat-ownership-operator.mjs`는 별도 승인 전의 **미검증 프로토타입**이다. 기본적으로 실행을 거부하며, 해당 거부는 검토 대기 표시이지 이관 절차의 안전 통제가 아니다. 운영 DB 연결 또는 적용을 시도하지 않는다. 기존 fixture 전용 프로그램과 구분한다.

- DB 변경 전 읽기 전용 캡처 단계에서 유일 사용자와 두 테이블의 행·컬럼을 조회한다. `SHOW CREATE TABLE`과 정보 스키마의 컬럼 목록이 완전히 일치해야 하며, 지원하지 않는 타입·생성 컬럼은 거부한다. 드라이버의 JSON 파싱을 피하려고 DB에서 컬럼별 `HEX(CAST(... AS BINARY))`로 변환한 값의 해시·대화 ID·건수를 보호 manifest에 남긴다. 이 값은 **SQL 논리 표현**으로, DB 엔진 내부 물리 바이트 보존을 뜻하지 않는다. 서로 다른 MariaDB 버전·타입·권한의 완전성은 미검증이므로 독립적인 실제 스키마·권한 대조와 별도 백업 복원 검증이 여전히 필요하다. manifest에도 식별자가 포함되므로 비공개 저장하고 보관·삭제 계획을 정한다.
- 컬럼 DDL 적용 후 별도 실행에서 서버 정체성, 계정, 캡처 해시와 컬럼, 데이터 및 NULL 소유권을 비교하고, 하나의 트랜잭션에서 변경 전후를 다시 대조하도록 작성했다. `updated_at`을 보존하며 결과 불명 커밋은 재시도하지 않는다. DDL 자체는 수행하지 않는다.
- 설정·manifest 파일의 소유자와 모드, TLS 서버 검증, 서버 식별값과 스키마 제약을 확인하도록 작성했다. 두 채팅 테이블에 대한 직접적인 `TRIGGER` 권한을 확인하고, 모호하거나 역할을 통해서만 부여된 권한은 거부한다. 채팅 테이블 트리거가 있으면 중단한다. ENUM은 표시 값과 숫자 인덱스를 함께 비교한다. 대용량의 경우 내용 조회 전에 각 테이블 논리 크기 4MB, 스레드 5,000행·메시지 10,000행을 넘으면 중단한다. 이 상한은 임의의 보수적 시험값이며 운영 적정성이나 반복 조회·잠금 시간의 상한을 보장하지 않는다. 권한 및 연결 방식은 운영 환경에 맞게 별도 검토해야 한다. 비밀과 행 원문은 로그에 출력하지 않는다.
- 앱 및 직접 DB 쓰기 차단, 진행 중 요청 정리, 운영 백업의 복원 검증, 백업과 manifest의 일치, 시간 중 드리프트, 기존 이력의 최종 설계와 승인 여부는 이 도구가 보장하지 않는다. 이들 중 하나라도 확인되지 않으면 실행하지 않는다. 또한 스키마의 인덱스·외래키·모든 DB 객체를 검증하는 도구가 아니다.
- Node 모의 단위 테스트는 `scripts/migrations/T-113-operator.test.mjs`에 있다. 작성자는 네트워크 비활성·합성 MariaDB 10.11.11에서 TLS 소켓 세션을 확인하고 capture, DDL 후 내용 변경·JSON 공백 변경·ENUM 빈 문자열 인덱스 변경 거부, 4MB 초과 중단, 정상 백필, 재실행 거부, 시각 보존을 시험했다. 제한된 열 권한의 계정은 정보 스키마에서 일부 열만 보고 `SHOW CREATE TABLE`은 거부되는 사례와, 한 테이블에만 TRIGGER 권한이 있어 다른 테이블의 트리거가 보이지 않는 계정의 중단도 재현했다. 소켓으로 연결 대상을 변경하는 테스트 전용 mysql2 preload를 사용했다. 운영 네트워크의 TLS·계정·접근 권한, 모든 타입·버전, 동시 삽입과 커밋 실패, 최종 수정본 독립 QA는 미검증이며 이 초안을 운영 실행 가능 판정의 근거로 쓰지 않는다. fixture 기동 단계, 예상 서버 포트, 누락된 테스트 도구 및 제한계정 권한의 시험 설정 오류가 있었고 수정한 재실행은 exit 0이다.

운영 적용 전에는 운영용 절차와 코드 완성, 독립 감사 및 QA, 실제 차단·요청 정리·백업/격리 복원 실증, 대상·소유자 재확인과 변경 승인, 운영 전 회귀 점검이 남아 있다. 최초 요청은 준비 결과 보고까지이므로 운영 데이터에 연결하거나 변경하지 않는다.
