## 1. 요약과 운영 중단 조건

운영 이관 전 `chat_threads`, `chat_messages`의 일관된 전용 백업을 암호화 보관하고, **별도 격리 DB**로 복원하여 이력과 스키마를 비교한다. 계정 확인에 필요한 최소한의 사용자 ID·생성시각은 별도 보호 manifest로 확인하며 `users` 전체를 덤프하지 않는다. DDL 뒤 실패 시 **백업 전체를 운영 DB에 자동 복원하지 않는다**. 정확한 영향 스레드의 소유자·수정시각을 원상 복구하는 별도 조건부 계획을 검토한다.

아래 중 하나라도 없으면 운영 백업·이관·복원을 진행하지 않는다.

1. 모든 채팅 쓰기·구버전 접근 경로와 진행 중 LLM 요청 정리 완료 증거. 행 잠금만으로 신규 INSERT 차단 불가.
2. 실제 대상 DB와 사용자, 암호화 키 수신자, 백업 위치·접근권한·보존 기간, 복원 실습 DB가 담당자에 의해 확정되고 안전하게 분리됨.
3. 아래 예시 명령이 운영 환경에서 재현 가능한지, 덤프 도구·암호화·복호·DB 최소 권한·압축/암호화 순서와 보호된 연결 방식이 확인됨.
4. 검증된 backup hash·복호·별도 DB 복원·전수 비교와 복원 담당자 확인. **백업 파일이 존재하는 것만으로 복구 가능하다고 판단하지 않는다.**
5. 운영 DDL의 명시 승인 및 검증된 귀속 DML과 절차·실행 범위, 배포 및 롤백 계획 확인. 사용자 계정 소유권 확인은 이들 운영 작업의 실행 승인을 뜻하지 않는다.

## 2. 대상·민감도·보존

| 항목 | 제안 | 위험과 조건 |
|---|---|---|
| 대화 이력 전체 스냅샷 | 변경 직전의 `chat_threads`, `chat_messages` 전체 및 두 테이블의 DDL·인덱스·FK를 일관된 읽기 스냅샷으로 보존 | 내용에 민감 정보가 있을 수 있으므로 화면·채팅·로그·외부 LLM으로 내보내지 않는다. |
| 소유자 확인 | 해당 사용자 ID·생성시각과 단일 사용자 확인만 보호된 manifest에 기록 | 이메일·이름·비밀번호 해시·키·토큰이 들어갈 수 있는 `users` 전체 덤프 금지. 이 항목도 민감정보로 보호. |
| 백필 대상 manifest | 각 대상 ID, 이전 owner, `updated_at`, 보관 상태와 부모별 메시지 수, 백필 후 기대 상태 | 차단된 전환 창에서 정확한 기존 NULL 대화 집합만 생성; DB 전체 또는 후속 생성 행과 혼동 금지. |
| 저장 | 서버 로컬의 접근 제한된 디렉터리, `umask 077`, 디렉터리 0700·파일 0600, 암호화 후 저장 | 경로·보존기간·오프호스트 사본과 접근 권한은 운영자가 지정하고 검증. 평문 dump를 NAS/Git/로그/클라우드에 남기지 않는다. |
| 키·인증 | DB 연결은 로컬 비밀 파일 또는 서비스 인증 프로파일을 통해 전달하고 키는 보호된 경로의 별도 파일 디스크립터/비밀관리 수단으로 제공 | 명령줄 인자·환경 출력·shell history·process listing·task 문서에 비밀번호나 키를 기록하지 않는다. `set -x` 금지. |

위 테이블만으로 누락 없이 복구 가능한지는 운영의 FK·트리거·참조 경로·권한·모든 인스턴스/장기 요청을 확인한 뒤 판단한다. 연관성이 밝혀지면 범위와 정보 취급을 재검토한다. 백업은 변경 전·쓰기 정지 후 하나의 일관된 시점에서 만든다.

## 3. 운영용 명령 틀 — 실행 금지, 환경 검증 전 예시

아래는 명령·담당·필요 정보를 검토하기 위한 **템플릿**이다. 자리표시자·접근 차단·비밀 저장·암호화 도구/수신자·복원 DB가 확정되지 않아 현재 실행 가능한 운영 런북이 아니다. 사용자 제공 확인과 별도로 프로젝트 규정상 운영 DDL에 명시 승인이 필요하다. 어떤 운영 SQL·덤프·서비스 변경도 이번 준비 작업에서 실행하지 않았다.

- **사전조건 (Leader/deployer + 독립 Reviewer):** 실제 대상 DB의 서버 식별과 schema, 엔진(InnoDB), FK/트리거, 작업자 DB 권한을 검토한다. 운영 전환 창에서 모든 채팅 읽기/쓰기 ingress와 대기 중·실행 중인 LLM 및 구버전 인스턴스 차단을 별도 문서의 방법으로 확인하고, 사용자·대화 대상 manifest를 보호된 저장소에 준비한다. 차단이 불완전하거나 신규 쓰기를 확인할 수 없다면 중단한다.
- **환경 (운영자 준비):** `<MYSQL_CNF>`는 0600의 독립 MariaDB 인증 설정 파일이며 CLI에서 첫 옵션으로 사용한다. `<AGE_RECIPIENT>`는 승인된 공개 수신자, `<BACKUP_DIR>`는 접근 제어된 0700 로컬 경로다. `<DB_NAME>`은 정확히 검증된 DB명, `<RESTORE_DB>`는 별도 폐기 가능한 격리 DB다. 실제 값이나 파일 내용을 로그에 쓰지 않는다. `mariadb-dump`, `mariadb`, `age`의 설치·버전·수신자/복호 키와 권한 확인은 아직 남아 있다.

```sh
# 검토용 형식 — 자리표시자와 ingress/비밀/복구 조건을 승인 전에는 실행하지 않는다.
set -euo pipefail
set +x
umask 077
# 출력 경로는 사전에 생성한 0700 디렉터리와 충돌하지 않는 신규 이름이어야 한다.
mariadb-dump --defaults-extra-file="<MYSQL_CNF>" \
  --single-transaction --skip-lock-tables --skip-add-locks --hex-blob --no-tablespaces \
  "<DB_NAME>" chat_threads chat_messages \
  | age -r "<AGE_RECIPIENT>" > "<BACKUP_DIR>/chat-before.sql.age"
chmod 600 "<BACKUP_DIR>/chat-before.sql.age"
sha256sum "<BACKUP_DIR>/chat-before.sql.age"
# 복원 리허설은 사전 생성한 별도 격리 DB에만 실행. 운영 DB 절대 금지.
# <PRIVATE_PLAINTEXT_DIR>는 사용 전 비어 있는 전용 0700 격리 임시 저장소다.
if ! age -d -i "<PRIVATE_IDENTITY_FILE>" "<BACKUP_DIR>/chat-before.sql.age" \
  > "<PRIVATE_PLAINTEXT_DIR>/verified.sql"; then
  rm -f "<PRIVATE_PLAINTEXT_DIR>/verified.sql"
  exit 1
fi
# 위 복호의 정상 종료를 확인한 뒤에만 import한다.
if ! mariadb --defaults-extra-file="<ISOLATED_MYSQL_CNF>" "<RESTORE_DB>" \
  < "<PRIVATE_PLAINTEXT_DIR>/verified.sql"; then
  rm -f "<PRIVATE_PLAINTEXT_DIR>/verified.sql"
  # 부분 복원 DB를 격리 유지하고 담당자가 폐기한다. 자동 재사용 금지.
  exit 1
fi
rm -f "<PRIVATE_PLAINTEXT_DIR>/verified.sql"
```

- 파이프 중간 실패는 전체 실패다(`pipefail`). 부분 암호문은 성공으로 취급하지 않고 보호된 위치에 격리해 담당자가 정리한다. 덮어쓰기 방지·공간 부족·암호화 수신자 오입력·키 복구·재시작 이후 복호 가능성은 운영 환경에서 먼저 확인해야 한다. 예시의 출력 파일 redirect는 **기존 파일을 덮을 수 있으므로**, 실제 실행 전 배타적 생성 방식의 운영용 명령으로 교체한다.
- 복호를 DB에 직접 파이프로 연결하지 않는다. 복호 도구는 무결성 실패를 알리기 전에 평문을 내보낼 수 있고 `pipefail`은 이미 적용된 SQL이나 암묵 커밋된 DDL을 되돌리지 못한다. 복호가 성공 종료된 뒤에만 격리 DB에 import한다. 복호 파일은 독립적으로 접근이 차단된 전용 0700 임시 저장소에 0600으로 생성하고, 가능하면 암호화된 임시 볼륨이나 tmpfs의 용량·swap·백업·덤프 정책을 미리 검토한다. 실패 출력물과 성공 후 평문은 삭제하고, 삭제 실패·강제 종료 시 잔여 파일을 격리하여 담당자가 확인·정리한다. 단순 삭제가 매체의 물리적 완전 소거를 뜻하지는 않는다.
- import 실패 시 격리 DB에 일부 SQL이나 DDL이 남을 수 있으므로 성공으로 표시하거나 재사용하지 않는다. 격리 DB와 대상 서버의 신원을 다시 확인한 담당자가 DB 전체를 폐기하고 새 DB로 처음부터 복원한다. 자동 `DROP`은 실행하지 않는다. 예시의 임시 파일명 역시 배타적 생성과 실패·신호 처리 검증이 필요하므로 운영용 실행 스크립트가 아니다.
- `--single-transaction`은 트랜잭션 테이블의 일관된 읽기를 돕지만 DDL/비트랜잭션 테이블·구버전 장기 쓰기를 차단하지 않는다. 대상 스키마가 실제로 InnoDB인지, 덤프 전후 DDL 및 외부 writer가 없는지는 별도 게이트다.
- 실제 비식별 보고에는 실행 시각, 환경 식별자(비밀 제외), 대상 테이블·기록 수, 암호문 SHA-256, 복구 검증 판정 및 담당자만 적고 SQL 본문이나 대화 내용·사용자 ID는 적지 않는다. 파일 권한·암호문 hash·암호화 recipient의 안전한 확인 방식을 정의한다.

## 4. 복원 검증 및 선택적 복구

1. 데이터가 운영 DB에 연결되지 않은 별도 MariaDB에만 백업을 복호·복원한다. 복원 명령에 프로덕션 접속 파일/DB 이름을 사용할 수 없도록 운영자와 Reviewer가 독립 확인한다. 비밀/평문 데이터가 임시 DB·파일에 남는 경로와 종료 후 정리 책임을 먼저 정한다.
2. 스냅샷 당시의 전체 스레드·메시지 수와 **정확한 대상 집합 및 실제 스키마의 모든 컬럼 값**을 보호된 환경에서 전수 비교한다. 비교 전에 원본·복원본의 스키마를 각각 열거해 컬럼명·순서·타입·NULL 허용 여부와 기본값을 대조하고, 누락·예상 밖 컬럼은 중단한다. 각 행의 모든 컬럼은 NULL 여부와 값을 비교하며 문자열·본문·JSON은 저장된 바이트 비교 가능 여부 및 문자셋·collation 변환을 확인한다. 공개 로그에는 불일치 건수만 남긴다. 인덱스·FK·트리거 등 DDL도 비교한다. 누락 또는 1건 이상 불일치하면 중단한다.

   체크아웃 `src/lib/db.ts`의 신규 생성 정의 기준 열은 다음과 같다. 이는 실제 운영 스키마의 증거가 아니며, 운영 DB에 실제로 존재하는 열과 새로 추가된 열까지 이관 직전 별도 열거한다. 확인된 기존 DB에는 `chat_threads.user_id`가 없었으므로 추가 전후 스키마 상태도 구분한다.

   - `chat_threads`: `id`, `user_id`(존재할 때), `title`, `symbol`, `created_at`, `updated_at`, `message_count`, `archived`.
   - `chat_messages`: `id`, `thread_id`, `role`, `content`, `draft_prompt`, `draft_prompt_raw`, `context_attached`, `llm_provider`, `llm_model`, `latency_ms`, `created_at`.

   이 컬럼의 실제 운영 전체 비교 도구와 실행은 아직 없다. 5절과 6절의 합성 시험은 각 fixture에 정의된 열만 비교했으며 위 목록 전체나 실제 스키마를 검증하지 않았다.
3. 귀속 DML은 정확한 영향 manifest와 사용자 확인이 일치할 때만 별도 검증된 도구로 수행한다. `updated_at=updated_at` 표현은 합성 fixture에서 별도 확인되었지만 전체 이관 검증은 아니다. 업데이트 전/후 행 집합·시각·건수·메시지 변경 0건을 확인한다.
4. 사고·결과 불명 시 접근 차단 상태를 유지하고 자동 재시도하지 않는다. DDL은 암묵 commit될 수 있으므로 `ROLLBACK`이나 앱 코드 되돌리기로 ALTER가 사라진다고 가정하지 않는다.
5. 원복이 필요한 경우 영향 manifest의 **정확한 행만** 현재 owner·수정시각·연관 메시지 등이 검증된 기대 후상태와 일치할 때에만, 별도 승인·독립 검토된 guarded transaction으로 변경 전 owner/수정시각을 복구한다. 어느 한 행이라도 변경·누락·새로운 처리 또는 비교 불가가 있으면 전체 중단, 부분 복구 금지. 새 대화나 사후 메시지를 덮어쓰지 않는다. 복구의 완전성은 row count뿐 아니라 exact ID set·값·시각·연관 메시지 비교로 검증한다.
6. 구버전 API는 owner를 무시하므로 차단 상태 없이 이를 재가동하지 않는다. 복원·코드 롤백·실제 사용자 접근 재개는 각각의 운영 절차와 담당자 판단을 따른다.

## 5. 합성 백업·복원 리허설 (실제 실행)

## 6. 운영 앱 호스트 도구 사전 확인과 대안 리허설

- 2026-11-04 읽기 전용 SSH 점검에서 `home_ubuntu`의 호스트명은 `home-dev-x600`, StockInvest `current`는 `releases/20261104-180613-a6b7605f`를 가리켰고 PM2의 온라인 `stockinvest`는 1개였다. 확인 결과 이 앱 호스트에 `age`, `age-keygen`, `mariadb`, `mariadb-dump` 명령은 없고 GnuPG **2.2.27**, Docker는 있었다. 도구 존재 여부만 확인했으며 비밀·실데이터·서비스 설정을 출력하거나 변경하지 않았다. 이는 시점 한정 관찰로, DB/NAS 호스트의 도구·접근 권한이나 운영 DB 접속 가능성을 뜻하지 않는다. 로컬 Docker 이미지 `mariadb:10.11.11`은 존재했으나 운영 서버 버전과 동일하다는 뜻은 아니다.

## 7. 실제 백업 경로 확인 (2026-11-04)

- 사용자 요청에 따라 실제 백업과 격리 복원을 준비하며 운영 DB에 읽기 전용 메타데이터 조회만 수행했다. MariaDB는 10.11.11이며 채팅 두 테이블은 InnoDB다. `have_ssl=DISABLED`였고 앱 DB 연결의 TLS 암호군은 빈 값이었다. 운영 채팅 내용과 계정 식별자는 조회·출력하지 않았다. 당시 메타데이터 조사 중 비밀번호 환경 변수명을 잘못 지정한 최초 연결은 인증 거부되었고, 앱의 실제 변수명을 확인한 후 읽기 전용 조회에 성공했다.
- 앱 호스트에 `mysql`과 `mysqldump`는 존재하나 `mariadb`와 `mariadb-dump`는 없다. 기존 문서의 MariaDB 명령 부재는 `mysql` 계열까지 부재라는 뜻은 아니다. 이 도구들과 운영 MariaDB의 덤프 호환성은 아직 확인하지 못했다.
- DB 호스트의 SSH 포트가 열려 있고 앱 호스트에는 해당 호스트 공개 키가 등록되어 있었지만, 기존 기본 계정·키로 비대화 인증이 거부됐다. 앱 호스트에서 이미 신뢰한 공개 키를 Mac의 일회성 접근 제한 known_hosts에 전달하고 엄격한 호스트 키 검증 아래 Mac 기존 계정·키로 시도한 결과도 인증 거부였다. 임시 known_hosts는 삭제했고 계정 추측·임의 키 수락·자격증명 출력은 하지 않았다.
- **결과:** TLS가 없는 DB 연결을 통한 실대화 데이터 전송은 실시하지 않았고, DB 호스트 내부 덤프 또는 신뢰된 암호화 터널 경로도 아직 확보하지 못했다. 따라서 이번 실제 운영 백업과 격리 복원은 미실시다. 안전한 접근 경로·키 관리 및 대상 데이터의 일관된 스냅샷을 확보한 뒤 다시 수행한다. writer 차단 전 백업은 그 시점의 복원 리허설일 뿐 차단 후 이관 직전 확정 백업을 대체하지 않는다.
- **MySQL 8 클라이언트 합성 호환성:** 앱 호스트의 `mysqldump`/`mysql` 8.0.46과 `--network none`, `--skip-networking` MariaDB 10.11.11 컨테이너의 임시 Unix socket을 사용했다. `--single-transaction --skip-lock-tables --skip-add-locks --hex-blob --no-tablespaces --column-statistics=0`로 합성 테이블 두 개를 덤프해 별도 합성 DB에 복원했다. 한글·ENUM·시각 및 FK를 포함한 소형 fixture에서 행 수와 대표 값 일치, exit 0을 확인했다. 처음 64MB 임시 DB는 초기화에 실패했고 512MB로 수정한 후 성공했다. 임시 컨테이너·파일을 정리했다. 실제 운영 스키마·트리거·전 컬럼, TLS 연결 및 운영 데이터의 호환성은 검증하지 않았고, 이 결과만으로 운영용 백업을 실행할 수 없다.
