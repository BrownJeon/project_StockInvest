## 현재 판정

**진행 불가(BLOCKED).** 운영의 모든 우회 경로를 막았다는 증거와 구버전 챗봇 처리·대기 작업이 0건이라는 증거가 아직 없다. DB 작업보다 먼저 두 조건을 모두 충족해야 한다. 사용자 확인에 따라 기존 대화는 현재 계정 소유로 취급하되, 소유권 인가가 없는 구버전으로 새 스키마를 개방해도 된다는 뜻은 아니다. 2026-11-04 후속 지시는 접근 차단·요청 정리와 백업 검증을 승인했고 운영 DB 변경 전 보고를 요구했다. 동일한 차단 승인 재요청이 필요한 것은 아니나 적용할 수 있는 차단 방법과 복구·매매 영향의 증거가 없는 상태에서 완료로 판정하지 않는다.

### 확인된 근거와 한계

- 2026-11-04 23:38 KST 운영 호스트 읽기 전용 재관찰: stockinvest와 stockinvest-cron은 모두 online이며 릴리스 `20261104-180613-a6b7605f`에서 실행됐다. 3003은 `0.0.0.0` 리슨했고 활성 stock nginx는 `/`을 127.0.0.1:3003으로 전달했다. 활성 sites-enabled 파일 중 문자열 `:3003`을 참조한 것은 stock 설정뿐이지만 동적 경로·다른 프록시·외부 라우터의 완전한 목록은 아니다. `/etc/nginx/sites-available`은 현 접속 계정에 쓰기 권한이 없고 `sudo -n`, nft 및 iptables 읽기 확인은 실패했다. docker 그룹 소속만으로 상위 권한을 우회해 설정을 변경하지 않았다. 관찰 시 웹 프로세스의 자식은 없었으나 작업 대기열·원격 요청 완료 증거는 아니고, 별도 Claude 프로세스 네 개는 상위가 해당 웹 프로세스가 아니므로 챗봇 작업이라고 판단하거나 일괄 종료하지 않았다. 방화벽·우회·진행 요청을 모두 확인할 수 없어 차단·종료 및 운영 설정 변경은 실시하지 않았다.
- 같은 시점 Mac에서 호스트의 첫 번째 LAN 주소로 TCP 3003 직접 연결에 성공했다(HTTP 요청·인증·본문 전송 없음). 실제 LAN에서 nginx를 거치지 않는 포트 접근이 가능하므로 nginx만으로는 차단할 수 없다. 나머지 세 후보 주소에서는 연결 시간이 초과되었고, 이것은 다른 출발지나 우회 경로 전체 차단의 증거가 아니다.

- 2026-11-04 22:52 KST 운영의 읽기 전용 관찰에서는 웹 프로세스가 `0.0.0.0:3003`에 리슨했고, stock nginx 가상 호스트의 `location /`는 `127.0.0.1:3003`으로 전달했다. `/api/chat` 전용 차단은 관찰되지 않았다. UFW 설정은 disabled였으나 nft 규칙은 비대화형 sudo 권한이 없어 확인하지 못했다. 이는 3003이 인터넷에서 실제 접근 가능하다는 증거도, 불가능하다는 증거도 아니다. 실행 직전 재확인한다.
- 저장소 `ecosystem.config.js`는 웹 1개를 `next start -H 0.0.0.0 -p 3003`으로 실행하고 autorestart를 설정한다. 프로세스 수와 실행 릴리스는 운영 시점에 재확인한다. 소스의 상태와 운영 릴리스는 같다고 가정하지 않는다.
- `src/lib/llm/provider.ts`의 Claude 대기는 프로세스 내부 Promise 큐이며 호출당 최대 3회 시도한다. HTTP 계열은 동시 실행한다. 챗봇 draft는 호출당 60초, messages는 선택적 정제 60초에 분석 120초를 이어 호출한다. 재시도·앞선 큐 대기 때문에 120초 대기 후 안전하다고 판정할 수 없다. 연결 종료도 서버 처리가 끝났다는 증거가 아니다.
- `scripts/cron-runner.sh`는 기본 `http://localhost:3003`에 `/api/cron/*`을 POST하며 매매 관련 작업을 포함한다. 웹 전체 차단·중지는 cron과 매매·알림에 영향을 줄 수 있다. 기존 스크립트도 curl 시간 초과 후 서버 작업이 계속될 수 있다고 경고한다. cron을 중지하거나 재시작하는 방안은 이번 준비에 포함되지 않는다.
- 소스의 챗봇 API 경로는 `/api/chat/models`, `/api/chat/threads`, `/api/chat/threads/[id]`, 하위 `/draft`, `/messages`다. 이 목록만으로 다른 경로나 우회 프록시의 부재를 증명할 수 없으므로 운영 릴리스와 라우팅 전체를 조사한다.

## 선행 작업: 운영자가 승인 전 완료해야 할 검증

1. **서비스 운영자**가 운영 서버, 로드밸런서·프록시·VPN·LAN·로컬 호출자와 IPv4/IPv6 경로를 목록화한다. 웹에 연결하는 모든 다른 프로세스와 앱 인스턴스, 직접 포트 접근, 중간 프록시와 기존 HTTP keep-alive 연결을 포함한다. 호스트 방화벽·클라우드/라우터 ACL의 실효 규칙을 권한 있는 담당자가 확인한다. 읽기 실패·불명 경로가 하나라도 있으면 중단한다.
2. **개발자/검증자**가 운영과 같은 구성의 격리 환경에서 챗봇 경로에 대한 일시 접근 차단 장치를 마련한다. nginx 하나만 적용하는 방식은 3003 우회를 막는 실효 제어가 함께 검증된 경우에만 후보가 된다. `GET/POST/PATCH/DELETE` 및 운영 버전에서 실제 사용하는 모든 메서드, 하위 경로, 쿼리와 슬래시·URL 정규화 변형, 인증된 기존 세션, 이미 연결된 keep-alive에서 차단을 재현한다. `/api/cron/*`과 일반 서비스가 영향을 받지 않는지도 별도 확인한다. 미확인 경로·우회·cron 영향 시 차단안을 폐기한다. 인증 검증은 격리된 시험 계정을 사용하고 대화 내용·쿠키·비밀을 기록하지 않는다.
3. **개발자/검증자**가 구버전의 진입 직후부터 최종 DB commit/rollback 및 비동기 후속 작업 종료까지 추적 가능한 활성 요청·대기 작업 계측 또는 동등하게 증명 가능한 격리/종료 수단을 설계·구현·검증한다. 인스턴스별 수치, 게이트 차단 이후의 race, 연결 해제·예외·재시도·queue 대기·process crash·provider 비동기 작업 및 마지막 DB 쓰기를 다룬다. 계측을 새 릴리스에만 넣으면 **이미 구버전에서 시작된 작업은 추적하지 못하므로** 구버전 작업 종료 증거가 별도로 필요하다. 로그·socket·일정 시간 대기만으로 0건 판정하지 않는다.
4. **서비스 운영자와 매매 담당자**가 서비스 중지 또는 구버전 종료가 꼭 필요한 대안인지 검토한다. 웹 중지가 cron API와 매매에 주는 영향을 해소하고 작업 중복·유실, 실행 중 주문·외부 AI 작업을 다룬 별도 안전 절차가 검증되기 전에는 `pm2 stop/restart`, 프로세스 강제 종료, cron 중단을 사용하지 않는다. 외부 provider 작업이 끝나지 않았어도 웹을 종료하면 응답/대화 저장이 유실될 수 있다.
5. **백필 담당자**와 차단 시점부터 백업·복원 검증, 백필, 새 버전 검증, 롤백까지 차단 유지 범위와 각 단계 증거·책임자를 맞춘다. 서비스 영향, 유지 시간, 실패 시 소통 및 거래 영향이 구체화되지 않으면 운영 일정을 확정하지 않는다.

## 실행 직전 읽기 전용 확인 명령

아래는 **향후 운영자가 읽기 전용으로 수행할 후보**이며 이 문서 작성 시 실행한 새로운 운영 변경은 없다. 실제 호스트/권한·프로세스 이름을 식별한 뒤 사용한다. 민감한 환경변수, 인증 헤더, 쿼리 결과, 원문 대화는 수집하지 않는다.

```sh
# 운영 호스트, 시간, 포트 리스너. 권한 부족으로 PID가 없으면 원인 확인 후 중단.
hostname
date -Is
ss -lntp '( sport = :3003 )'

# 해당 PM2 계정으로 실행. 필드만 출력하며 환경변수는 출력하지 않는다.
pm2 jlist | node -e 'let s="";process.stdin.on("data",x=>s+=x);process.stdin.on("end",()=>{for(const p of JSON.parse(s))if(["stockinvest","stockinvest-cron"].includes(p.name))console.log(JSON.stringify({name:p.name,pid:p.pid,status:p.pm2_env?.status,cwd:p.pm2_env?.pm_cwd,restarts:p.pm2_env?.restart_time}))})'

# 방화벽 전체 확인은 권한 있는 운영자가 별도 비공개 증빙으로 수행.
# 다음 명령이 실패하면 미확인 상태이며, 우회 차단 성공으로 취급하지 않는다.
sudo -n nft list ruleset >/dev/null
```

마지막 명령의 성공은 **규칙을 읽을 수 있다는 뜻일 뿐 차단 성공이 아니다**. 담당자가 실제 규칙과 IPv4/IPv6, upstream ACL, 로컬 우회를 검토하여 출발지별·대상별 결과를 증빙한다. `ss`는 수신 포트 확인용이며 작업 큐의 완료를 증명하지 않는다. PM2 출력이 누락되거나 예상과 다르면 중단하고 조사한다.

### 차단 중 새 릴리스의 검증 경로 (후보, 미구현)

일반 chat 유입을 계속 막는 동안 검증을 수행하려면 별도의 신뢰 경로가 필요하다. 단순히 `localhost`나 특정 IP를 예외로 열면 같은 호스트의 다른 프로세스 또는 해당 IP를 공유하는 다른 호출자도 이용할 수 있어 허용 기준이 아니다. 다음은 **후보 설계**이며, 실제 환경에서 구현·검증되거나 운영 권한이 확인된 것은 아니다.

1. 실제 운영과 유사한 **별도 격리 서비스·별도 합성 DB**에서 두 합성 계정으로 본인 접근과 타인 대화 거부, 무세션 거부, 작성·삭제 등 기능을 검증한다. 이 결과는 실제 운영 DB·세션에 대한 증거가 아니다.
2. 운영 검증이 필요한 경우, 전체 차단이 유지된 상태에서 새 인가 릴리스에만 연결되는 임시 검증 경로를 별도로 구성한다. 예를 들어 전용 OS 사용자와 접근 권한이 제한된 Unix 소켓을 사용하는 관리용 프록시 후보를 검토한다. 프록시가 실제 적용된 chat 차단을 통과하는 경로라면 **신뢰된 검증자만** 해당 예외에 접근할 수 있어야 한다. 소켓 디렉터리 소유권·부모 디렉터리 권한·심볼릭 링크·프로세스 자격·우회 포트·전달 대상 릴리스와 시간 제한을 격리 환경에서 시험하고, 연결 중인 요청이 있어도 예외를 닫으면 신규 요청이 차단되는지 확인한다. 동일 OS 계정의 다른 프로세스가 접근할 수 있으면 별도 신뢰 경계가 아니므로 사용하지 않는다. 실제 운영의 프록시·애플리케이션이 이 후보를 지원한다는 뜻은 아니다.
3. 검증 경로가 준비되면 정확한 담당자·목적·대상·허용 HTTP 메서드·시작 및 종료 시각을 기록한다. 검증 요청은 사용자 확인을 받은 기존 계정의 인증을 이용한 읽기 위주로 한정한다. 비밀값·쿠키·대화 원문을 기록하지 않는다. 별도 승인 없이 사용자·대화 생성, 메시지 전송·삭제나 외부 LLM 호출은 하지 않는다.
4. 제한된 검증을 마친 뒤 새 진입을 닫고 검증용 진행 요청과 최종 DB 작업이 끝났음을 확인한다. 예외 규칙·소켓·전용 자격을 해제 또는 폐기하고, 새 연결과 기존 keep-alive 연결에서 그 경로가 다시 차단되는지 시험한다. 일반 차단은 이 작업이 끝나도 유지한다. 검증 경로가 남았거나 그 종료를 확인할 수 없으면 개방하지 않는다.

과거 운영 집계에서는 계정이 하나였다. 두 번째 실계정이 없는 상태의 무세션 거부나 존재하지 않는 계정 거부는 **실제 타 사용자 간 소유권 차단 시험이 아니다**. 운영에서 해당 시험을 반드시 요구하는지 이관 책임자가 정하고, 요구한다면 적법한 별도 계정과 데이터 준비·변경 승인 없이 새 계정을 만들지 않는다. 준비할 수 없으면 그 항목은 미검증으로 기록하며 필수 조건인 경우 개방을 보류한다. 운영 차단·검증 예외의 적용과 삭제, 계정 생성과 데이터 쓰기 여부는 각각 기존 운영 승인 절차를 따른다.

## 중단·롤백

- DB 변경 전 실패: 검증된 차단 장치의 정확한 역순 복구 절차를 운영자가 실행하고 사용자 기능·cron 경로를 확인한다. 변경하지 않은 구성 요소는 건드리지 않는다.
- DB 변경 중/후 실패: 먼저 챗봇 접근 차단을 유지한다. DB 백업·복원 실행안의 판단 및 복구 절차에 따른다. 구버전은 소유권 인가가 없으므로 단순히 구버전 기동이나 프록시 원복으로 서비스를 개방하면 안 된다. DB 스키마와 구버전 호환성, 데이터 보존, 인가를 검증하고 책임자가 판단하기 전까지 차단 유지한다.
- 어떤 단계에서든 매매·cron 영향이 관찰되면 매매 담당자에게 즉시 보고하고, 미리 검증된 대응만 사용한다. 주문을 재시도·취소하거나 cron을 임의 재시작하지 않는다.

## 남은 필수 증거

1. 권한 있는 운영자의 실제 경로/방화벽 목록과 구버전 코드·실행 프로세스 확인.
2. 구버전·직접 포트·연결 유지 우회를 막되 cron 경로를 보존하는 차단 장치의 격리 검증 결과와 정확한 적용/역순 복구 명령. 현재 미구현이므로 구체적인 운영 명령을 지어내지 않는다.
3. 기존 요청·큐·최종 DB 쓰기 0건을 증명하는 방법의 구현·격리 테스트와 구버전 적용 방법. 현재 미확보.
4. 매매 영향과 실제 점검 시간창, 사용자 기능 확인 및 승인. 백업·복원·백필 담당자와 조건 연계.

이 문서의 조사·절차 초안만으로 운영 차단이나 드레인 성공을 주장하지 않는다.

## 추가 준비: 차단 경계와 구현 후보

다음은 적용 명령이 아니라 **구현·검증할 후보**다. 운영 방화벽·nginx 구성 및 권한이 미확인이므로 그대로 실행할 규칙을 만들거나 그 효과를 보장할 수 없다.

| 경계 | 후보 제어 | 통과 조건 |
|---|---|---|
| 외부 → nginx | 모든 가상 호스트에서 `/api/chat` 네임스페이스를 유지보수 응답으로 막는다. 차단 여부는 요청별로 판단한다. | 실제 운영 라우터의 디코딩·정규화 기준으로 모든 메서드·변형 및 기존 연결을 시험하고, 다른 가상 호스트와 다른 프록시 우회가 없음을 확인한다. 새 세션뿐 아니라 이미 로그인한 세션도 거부한다. |
| 외부/LAN → 3003 | 권한 있는 운영자가 서버·라우터·방화벽에서 3003 직접 접근을 차단하는 실효 규칙을 설계한다. IPv4·IPv6와 모든 네트워크 인터페이스, 이미 성립된 연결에 대한 처리까지 포함한다. | 외부·LAN의 실제 대표 출발지마다 신규 및 기존 연결 모두 차단; 검증하지 못한 출발지가 있으면 실패. 로컬의 단순 curl 성공/실패만으로 외부 경계를 판단하지 않는다. |
| 같은 호스트 → 3003 | nginx와 `stockinvest-cron` 등의 합법 호출자를 포함해 프로세스·계정·네임스페이스별 목록을 만든다. 앱 계층 공통 게이트로 모든 요청을 검사하거나, 운영 커널/방화벽이 지원하는 검증된 프로세스별 로컬 접근 제어를 사용한다. | 같은 호스트에서 승인되지 않은 프로세스가 직접 chat을 호출하지 못하고 nginx·cron 호출은 필요한 범위에서 동작해야 한다. `127.0.0.1` 접근 가능만으로 호출자를 신뢰하지 않는다. |
| cron → 3003 | 승인된 cron의 `/api/cron/*`은 유지하고 사용자 chat과 분리한다. | 현재 cron 러너와 실제 라우팅을 확인하고, 격리 시험으로 cron 필수 경로 및 인증이 유지됨을 입증한다. 단순히 포트 3003 전체를 막으면 실패다. |

**중요한 제약:** 호스트 방화벽의 포트/주소 규칙은 보통 HTTP 경로를 판별하지 못한다. 따라서 동일 3003 포트에서 cron만 허용하고 chat만 막으려면 신뢰할 수 있는 호출자별 접근 통제와 프록시/앱 계층의 경로 제어가 함께 필요하다. 예를 들어 `localhost` 전체를 허용하면 그 호스트의 다른 프로세스도 chat에 직접 접근할 수 있으므로, 모든 로컬 호출자를 신뢰하고 그 목록의 완전성을 검증할 수 없다면 이 후보는 실패다. 앱 공통 게이트는 현재 운영 구버전에 존재한다고 확인되지 않았으며 이를 새 릴리스에 도입하려면 별도 개발·배포와 그 전환 안전성 검증이 필요하다.

**적용·되돌리기 준비:** 서비스 운영자와 네트워크 담당자가 위 후보 중 실제 구성에 맞는 것을 고르고, 기존 설정의 버전·해시와 변경 전/후 규칙, 정확한 적용/되돌리기 명령, 자동 재시작과 기존 연결 처리, 규칙 순서를 격리 환경에서 고정한다. `/api/chat` 외의 대체 라우트가 운영 릴리스에 있다면 동일하게 포함한다. nginx 경로 차단과 3003 직접 경로 차단 중 하나라도 불완전하면 백필에 진입하지 않는다. 권한: nginx 검증·적용 권한과 실효 호스트/상위 네트워크 정책을 읽고 변경할 수 있는 권한이 각각 필요하다. 방화벽 상태만 보는 `sudo -n nft list ruleset`의 성공은 어느 권한이나 적용 효과를 보장하지 않는다.

## 추가 준비: 구버전 작업 종료의 입증

구버전의 메모리 큐는 외부에서 직접 관측할 계측이 확인되지 않았다. 따라서 새 계측 릴리스의 활성 수치가 0이어도 과거 프로세스의 작업이 끝났다는 증거가 아니다. 운영 책임자가 아래 중 하나를 **격리 환경에서 먼저 구현·검증**해야 한다.

1. **무중단 계측 후보:** 구버전의 모든 chat 진입 지점에 차단과 추적을 원자적으로 걸고, 이미 들어온 요청까지 인스턴스별로 추적한다. 요청 접수부터 큐 대기, provider 응답, 마지막 DB commit/rollback과 후속 작업 종료까지의 소유 관계를 기록한다. 게이트 적용과 계측 시작 사이의 누락, 재시도·예외·클라이언트 연결 종료·프로세스 crash·다중 인스턴스 처리까지 실험한다. 현재 구버전에서 동작하는 계측 설치 방법은 미확인이라 이 후보는 아직 실행할 수 없다.
2. **구버전 프로세스 종료 후보:** 모든 chat 유입을 먼저 차단하고, 서비스/매매 담당자가 웹 전체 중지의 cron·매매·기존 요청 영향과 유실을 해결한 후, 별도로 승인된 정상 종료 절차를 쓴다. 운영자가 기존 웹 인스턴스의 PID·시작 시각·릴리스·프로세스 그룹/cgroup과 자식·별도 워커를 식별하고 재기동 경로까지 확인한다. 정상 종료 후에도 원래 인스턴스 및 그 작업을 수행할 자식·별도 워커가 존재하지 않고 해당 DB 세션·트랜잭션과 서버측 후속 작업이 더 이상 쓰지 못함을 DBA가 독립적으로 확인한다. provider 측 작업이 남는지, 남으면 결과 저장·과금·중복 요청에 어떤 영향을 주는지도 확인한다. PID 소멸만으로 provider나 다른 프로세스의 후속 쓰기 중단을 추정하지 않는다. 전체 거래·cron 영향과 DB 연결 식별 방법이 미확인이므로 이 역시 현재 실행 불가다.

둘 다 실패하거나 증거가 누락되면 드레인 완료 판정은 불가하다. 예상 대기 시간은 참고치일 뿐 성공 기준이 아니다. 실행 책임자는 서비스 운영자, DB 세션과 트랜잭션 판정 책임자는 DBA, 외부 provider 작업 판정 책임자는 해당 서비스 운영자다. 필요한 접근은 프로세스/자식·재시작 정책 읽기, 승인된 서비스 제어, DB 세션·트랜잭션 조회 및 provider 작업 상태 확인 권한이다. 운영의 실제 권한·실행 방법과 종료 후 다른 기능 복구 절차는 아직 확인하지 못했다.

## 후속 준비: 적용 가능한 경로 선택과 증거표

**선택 전 상태: 두 후보 모두 미검증·운영 실행 불가.** 구버전에 이관 전부터 작동하는 추적 장치가 있는 증거가 없으므로, 새 릴리스에 추적기를 추가하는 것만으로 기존 요청을 드레인할 수 없다. 이관 책임자는 실제 릴리스와 운영 경로를 확인한 뒤 아래 중 하나를 선택한다. 어느 후보도 다른 서비스나 DB 직접 작성자를 자동으로 통제하지 못한다.

| 후보 | 실제 수행 전 필요한 준비 | 중단 조건 |
|---|---|---|
| A. 기존 구버전을 유지하며 드레인 | **이미 시작된 요청까지** 완전하게 식별할 수 있는 구버전 호환 계측 방법, 누락·경합 시험과 배포 없이 적용할 수 있는 수단을 제시한다. 차단 후 해당 프로세스의 접수부터 마지막 쓰기까지 0건임을 증명한다. | 이전부터 실행 중인 요청이나 큐가 계측 대상에서 빠질 수 있거나, 계측을 위해 먼저 구버전을 바꾸어야 하는 경우. 현재 이 조건을 충족하는 방법은 없다. |
| B. 웹 프로세스 전환을 포함한 격리 | 모든 chat 작성 경로에 외부 차단을 유지하고, 구버전 및 그 후속 작성자가 더는 DB에 쓸 수 없는 상태를 증명한 뒤 새 인가 버전으로 전환한다. 웹 중단 시간의 cron·매매·알림 영향과 실패 대응, 기존 요청의 결과 유실 처리에 대한 별도 계획 및 동의가 필요하다. | 매매 안전·기존 대화의 유실 여부·프로세스 재기동·직접 DB 작성·연결된 provider 작업 중 하나라도 판정 불가. `pm2 stop` 또는 `restart`만으로 통과하지 않는다. |

**B의 전환 순서 초안:** ① 사용자·DB 작성 경로와 인스턴스를 빠짐없이 식별하고 비공개 변경 전 설정을 보관한다. ② 경로별로 격리 시험된 차단을 건 뒤 새 chat 요청이 전달되지 않음을 확인한다. ③ 매매 담당자가 승인한 정지·대체 방안으로 웹 구버전을 종료하고 자동 재기동을 통제한다. ④ 확인된 프로세스 그룹과 별도 워커의 종료뿐 아니라 구버전이 생성한 모든 DB 세션·트랜잭션과 다른 작성 경로의 종료 또는 차단을 DBA가 확인한다. ⑤ 차단을 유지해 백업·복원 검증 및 백필을 수행한다. ⑥ 새 버전의 소유권 인가와 회귀 검증 뒤에만 단계적으로 개방한다. 이 순서는 **설계 후보**이며 정확한 명령, cron 연속성 및 역할별 복구 절차는 아직 만들어지지 않았다. 특히 정지 중 작업이 완료되지 않은 사용자의 응답을 잃을 수 있으므로 이관 후 건수만 같다고 보존 완료로 판정하지 않는다.

### 판단에 사용할 증거의 최소 단위

| 증거 | 수집·판정 책임 | 필수 판정 |
|---|---|---|
| 운영 릴리스·프로세스 명세 | 서비스 운영자 | 실행 중인 각 인스턴스의 PID **및 시작 시각**, 실행 릴리스, 부모·자식·별도 워커, 재기동 경로, 앱 계정과 호출자 목록을 확인한다. PID 단독은 재사용될 수 있어 식별 증거로 부족하다. PM2 등록 목록만으로 외부 프로세스 부재를 단정하지 않는다. |
| 출발지별 접근 표 | 네트워크·서비스 운영자 | 인터넷·LAN·같은 호스트·다른 프록시·IPv4/IPv6 각각에 대해 기존 연결과 신규 연결, chat의 모든 실제 경로와 메서드, cron 유지 결과를 기록한다. 접근할 수 없어 시험하지 못한 셀은 PASS가 아니다. |
| DB 작성자·연결 표 | DBA | chat 테이블을 수정할 수 있는 계정·서비스와 직접 작성자, 구버전이 사용한 세션·열린 트랜잭션을 식별하고 차단 후 전부 종료 또는 해당 권한의 차단을 증명한다. 커넥션 풀과 다른 업무의 공유 계정 가능성을 고려한다. 계정 전체 권한 회수는 매매 업무에도 영향을 줄 수 있어 임의로 하지 않는다. 스냅샷 1회의 세션 0건은 향후 재연결 방지의 증거가 아니다. |
| 외부 작업 및 손실 기록 | 서비스·provider 운영자 | Claude 자식 프로세스와 원격 provider 요청의 상태·종료 가능성을 별개로 기록한다. 원격 완료 여부를 알 수 없으면 중복 호출·추가 과금 및 응답 유실 가능성을 미해결로 기록하고 이관 책임자가 중단한다. 로그에 프롬프트·응답·토큰·인증정보를 남기지 않는다. |
| 매매·cron 연속성 | 매매 담당자 | cron이 웹과 동일 포트를 쓰는 사실을 반영해 작업 시간대, 실행 중 작업, 알림 공백 및 재개 후 중복·누락 확인 방안을 사전에 검증한다. 실제 주문을 시험 목적으로 발생시키지 않는다. |

작업 트리에서 확인한 `claude-cli.ts`에는 provider 큐 외에도 모듈 전역 Promise 큐가 있으며 CLI를 자식 프로세스로 실행한다. 같은 큐/프로세스 자원을 다른 업무도 사용할 수 있으므로 chat만을 위한 자식이라고 단정하거나 일괄 종료하면 안 된다. `ecosystem.config.js`의 웹 프로세스는 `autorestart: true`이며 cron도 별도 자동 재시작 프로세스다. 이는 **현재 작업 트리 근거**이고 관찰된 운영 릴리스와 일치한다는 보장은 없다. 운영 릴리스의 해당 구현·설정을 별도 비교해야 한다.

## 로컬 격리 모의 검증

2026-11-04 별도 `/tmp/t113-access-drain-simulation.cjs`를 생성하여 로컬 임시 포트의 모의 Node HTTP 서버만 사용했다. 실행 명령은 `node /tmp/t113-access-drain-simulation.cjs`다. 결과는 ① 클라이언트 연결 종료 후 모의 서버 작업이 계속 진행됨 ② 모의 게이트가 동일 keep-alive 연결의 chat 요청을 503으로 차단하면서 모의 cron 요청은 200을 반환함 ③ 기존 모의 요청이 게이트 적용 뒤 쓰기를 수행하고 활성 수치가 나중에 0이 됨 ④ 게이트 제거 후 모의 cron 호출이 정상인 것을 확인했다. **이 시험은 재현 모델의 동작만 보여 주며**, 실제 Next.js, nginx, OS 방화벽, 실제 구버전 큐나 운영 경로의 안전성·적용 가능성은 검증하지 않았다. 운영 서버와 DB에 접속하거나 설정을 변경하지 않았다.
