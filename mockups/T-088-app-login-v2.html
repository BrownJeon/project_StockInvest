이 데모는 화면 모양만 보입니다. 이메일 칸의 you@example.com 은 입력란 안내 글자(placeholder)이고, 로그인 과정의 코드·검증값·토큰은 어느 화면에도 그리지 않습니다(구현도 같습니다).

v1 → v2 무엇이 바뀌었나

  • 화면은 하나입니다. 웹과 앱이 같은 login/page.tsx 와 같은 Google 버튼 컴포넌트(OAuthButtons)를 씁니다. v1 의 앱 전용 컴포넌트(AppLoginArea)는 만들지 않습니다.
  • 앱만 다른 것은 두 가지뿐입니다. ① Google 을 누르면 Chrome 창이 열립니다(웹은 같은 창 이동). ② 그 뒤의 대기·오류 상태입니다. 상태는 모두 Google 버튼 바로 아래 같은 자리에 나타납니다.
  • GitHub 는 화면 코드와 문구에서 뺍니다. 운영 웹의 로그인 화면은 이미 Google 하나라 보이는 모습은 그대로입니다. 서버 라우트는 건드리지 않습니다.
  • 정리한 것: 앱 전용 "oauth_account" 문구와 앱 전용 안내 줄은 없앴고, 결정 항목은 6개에서 5개로 줄여 모두 권고값을 달았습니다("권고대로"라고만 답하셔도 됩니다).

웹에서 글자가 달라지는 곳은 세 군데뿐입니다 — ① 이메일 미인증 안내의 "Google/GitHub" → "Google"(D·G 절), ② 설정 › 앱 설치 안내 ③ 문구(웹에서도 보이는 안내 — G 절), ③ D5 에서 A 를 고르면 이메일 로그인 오류 문구의 "아래" → "위의"(E 절). 로그인 화면의 모양·배치는 웹에서 그대로입니다.

A. 웹 로그인 화면과 앱 로그인 화면 — 같은 화면

아래 두 화면은 같은 한 개의 틀에서 만들어집니다(구현에서는 같은 컴포넌트). 제목·Google 버튼의 모양과 문구·"또는 이메일로" 구분선·이메일 폼·가입 링크가 같고, 데모가 두 화면의 HTML 을 실제로 비교해 결과를 보입니다. 맨 오른쪽은 참고용 현재 앱(v1.0.0)입니다.

서버 Google 설정 (서버가 알려 주는 목록 — 웹·앱 같음)

웹 브라우저 — 지금과 같음 (보이는 변화 없음)

앱 — 제안: 웹과 같은 화면

참고 — 앱 현재 v1.0.0 (소셜 버튼 없음)

비교는 첫째·둘째 화면의 HTML 문자열(요소·글자·순서·속성, 안쪽 id 이름의 접두어만 제외)을 데모가 직접 대조한 결과입니다. 안내 영역(role="status")은 웹에도 그려져 있지만 비어 있어 보이지 않습니다 — 그래서 첫 화면 그리기가 웹·앱 같습니다.

로딩·빈 상태: 서버가 Google 설정 목록을 알려 주기 전에는 아무것도 그리지 않고(웹·앱 같음, 깜빡임 없음), Google 이 설정되어 있지 않으면 버튼과 구분선이 통째로 없고 이메일 폼만 남습니다 — 위 "없음"을 눌러 확인하세요. "초대코드가 없으신가요? 가입 요청" 줄은 지금처럼 서버에 메일 발송 설정이 있을 때만 보입니다(웹·앱 같음).

데스크톱(1280px): 로그인은 가운데 카드(최대 380px)라 넓은 화면에서도 같은 모양입니다 — 바뀌는 것 없음. C·D 의 상태 중 앱 전용은 웹 화면에 나타나지 않습니다.

B. 웹과 앱의 차이 — 로그인 화면(/login)에서는 이 두 가지뿐입니다

두 번째 차이는 화면이 아니라 클릭 동작이고, 사용자에게 숨길 수 없어서 솔직하게 적습니다. Google 이 앱 안(WebView) 로그인을 disallowed_useragent 로 막기 때문에 앱은 Chrome 창을 따로 열어야 합니다.

C. 앱에서 Google 을 누른 뒤 — 대기·마무리 상태 (앱에서만)

Google 버튼은 그대로 두고, 그 바로 아래에 상태가 나타납니다. 대기 중에는 버튼이 잠기고(같은 일을 하는 버튼이 둘이 되지 않게) 카드의 [Chrome 창 다시 열기]가 그 역할을 합니다. 이메일 폼은 어느 상태에서도 잠그지 않습니다. 라디오로 상태를 고르거나 미리보기 안 버튼과 "데모 사건" 버튼으로 흐름을 따라가 볼 수 있습니다.

D. 오류 상태 — 로그인이 안 된 경우 (카드 맨 위 안내 상자)

오류는 지금처럼 로그인 화면 주소에 고정 코드(?oauth_error=)를 붙여 다시 띄우고 카드 맨 위 안내 상자에 보입니다. 다시 시도하는 행동은 바로 아래 [Google로 계속하기] 하나입니다. 웹에도 있는 코드 3개(취소·실패·이메일 미인증)는 웹과 앱의 문구와 상자가 글자까지 같고, 나머지 3개는 앱 로그인에서만 생깁니다.

E. 이메일 로그인에서 "소셜로 가입된 계정"(oauth_account) 문구 — 앱 전용 문구를 없앱니다

T-084 는 앱에 Google 버튼이 없어서 서버 문구가 막다른 말이 되자 앱 전용 문구를 만들었습니다. 이제 앱에도 같은 Google 버튼이 있으므로 앱 분기를 없애고 웹·앱 공통 문구를 씁니다. 그런데 서버 문구의 "아래 Google로 계속하기"는 실제로는 위쪽 버튼을 가리킵니다(웹에서도 이미 그랬습니다 — 오류 줄은 비밀번호 칸 아래, Google 버튼은 카드 위). 이 방향을 고칠지가 D5 입니다. 소유자 계정은 Google 전용이라 이 문구를 가장 자주 만날 사람이 바로 소유자입니다.

D1. 앱의 가입 화면(/signup)에 Google 버튼을 둘까 새

F 절의 세 화면을 비교하세요. 로그인 화면(/login)은 이 결정과 무관하게 웹·앱이 같습니다.

A. 앱에서는 숨긴다 (지금과 같음)✓ 권고

앱 Google 로그인은 기존 계정만 들어옵니다. 가입 화면의 목적은 새 계정이라, 버튼이 있으면 새 사람에게는 항상 실패입니다. 가입은 웹에서(이메일 가입 폼은 앱에서도 그대로). 단점: 이 화면 하나는 웹과 다릅니다 — "같은 화면" 원칙의 유일한 예외.

B. 앱에도 표시한다

웹·앱이 글자 하나까지 같아집니다. 단점: 새 Google 계정이 누르면 Chrome 창까지 갔다가 "가입된 계정이 없습니다"(로그인 화면)로 돌아오는 막다른 길이 생깁니다.

D2. 가입되지 않은 Google 계정(signup_requires_web) 안내에 [Chrome에서 가입 화면 열기]를 둘까

A. 문구 + 버튼✓ 권고

앱 안에서는 가입할 수 없으니 Chrome 창으로 /signup 을 엽니다(앱 업데이트 받기와 같은 "외부 열기" 경로). 문구만 두면 "앱에서 할 수 있는 게 없는 안내"가 다시 생깁니다.

B. 문구만

범위가 가장 작습니다. 사용자가 브라우저를 직접 열어 주소를 입력해야 합니다. 초대제라 이 경우를 만날 사람은 적습니다.

D3. 대기 카드에 [취소] 버튼을 둘까

A. 둔다✓ 권고

누르면 검증값을 지우고 대기를 풀고 Chrome 창 닫기를 시도합니다. Chrome 창이 앱 위 탭이 아니라 별도 브라우저 앱으로 열리는 기기에서는 "창이 닫혔다"는 신호가 오지 않아 대기 카드에 남을 수 있는데[추측 — 실기기 확인 필요], 그때 빠져나갈 길입니다.

B. 두지 않는다

카드가 단순합니다. 창을 닫으면 자동으로 풀리고 이메일 폼은 계속 쓸 수 있어 갇히지는 않지만, 위 경우에는 10분 만료(D4 A)까지 카드가 남습니다.

D4. 대기 카드를 자동으로 풀까 (창을 닫았을 때 · 10분이 지났을 때)

A. 푼다 + 한 줄 안내✓ 권고

창이 닫히고 1.5초 안에 결과가 안 오면 "로그인 창이 닫혔습니다. 다시 눌러 주세요."로, 10분이 지나면 "로그인 요청 시간(10분)이 지났습니다. 다시 눌러 주세요."로 풀립니다. 로그인을 끝낸 직후에도 창이 닫히므로 1.5초 안에 결과가 오면 무시합니다. 10분은 서버 요청 유효시간과 같습니다.

B. 풀지 않는다

카드가 계속 "로그인하는 중입니다"로 남습니다. 사용자가 이미 그만두려고 창을 닫은 경우에도 상태를 잘못 말하고, 10분 뒤 [다시 열기]는 반드시 실패합니다.

D5. 이메일 로그인 "소셜로 가입된 계정" 문구의 "아래"를 "위의"로 고칠까 새

E 절의 가운데·오른쪽 화면을 비교하세요. 서버 응답은 바꾸지 않고 화면이 문구를 조립합니다.

A. "위의 Google로 계속하기를 눌러 로그인하세요"✓ 권고

Google 버튼은 오류 줄보다 위에 있습니다. 웹·앱이 같은 문장을 읽고 같은 곳을 누르게 됩니다. 단점: 웹의 보이는 문장에서 한 단어("아래" → "위의")가 바뀝니다("웹은 변하지 않는다"의 예외).

B. 서버 문구 그대로 ("아래")

웹이 한 글자도 바뀌지 않습니다. 단점: 버튼이 위에 있는데 "아래"라고 말하는 어긋남이 웹·앱 모두에 그대로 남습니다.

기본값으로 정한 것 — 결정 불필요, 바꾸고 싶을 때만 알려 주세요

  • 말투는 합니다체 — 이 화면의 기존 문구("계속하려면 로그인하세요")와 서버 문구가 모두 합니다체라 한 카드 안에서 섞이지 않게 맞췄습니다.
  • 앱이 도중에 다시 시작되어 검증값을 잃은 경우(app_verifier_lost)는 따로 안내합니다 — 서버에 묻기 전에 앱이 스스로 아는 사실이라 구분해서 말해도 서버 정보가 새지 않습니다.
  • 앱 [취소] 안내는 웹의 기존 문구("소셜 로그인을 취소했습니다.")를 그대로 씁니다 — 앱에서 취소 문구가 두 가지가 되지 않게.
  • Google 버튼은 서버가 Google 을 "설정됨"으로 알려 줄 때만 그립니다(지금 그대로). 앱도 같은 목록을 조회합니다.
  • 앱의 이메일 가입 폼은 지금 그대로 둡니다(이번 범위 밖).

설계 메모

  • 값을 그리지 않는다: 코드·검증값·세션은 화면·콘솔·주소 표시 어디에도 나오지 않습니다. 오류 코드(app_code_invalid 등)는 고정 문자열이라 주소에 붙어도 됩니다.
  • 거짓 안심 금지: "안전하게 로그인됩니다" 같은 말을 쓰지 않습니다. 대기 카드는 무슨 일이 일어나는지와 다음 행동만 말합니다.
  • 로그인 전 화면이라 DRY_RUN·KILL 표시와 업데이트 띠는 이번 범위 밖입니다(로그인 전에는 띠가 안 보임 — T-084 그대로).
  • 색만으로 구분하지 않기: 대기 = 회전 표시 + 제목 문장, 닫힘·만료·취소·열기 실패 = 원 안 "i"/"!" 기호 + 문장, 오류 = 상자 + 문장. 빨강 막대는 기존대로 email_unverified 하나뿐입니다.
  • 터치: Google·다시 열기 48px, 취소·가입 화면 열기 44px. 360px: 카드 안 문장은 줄바꿈(word-break: keep-all), 가로 스크롤 0.
  • 앱 판별은 표시 전용: isNativeApp() 은 누르기 동작과 버튼 아래 상태 표시에만 씁니다. 서버는 서명된 state 안의 platform=app 으로만 분기합니다(설계 ③). 웹 번들은 @capacitor/* 를 import 하지 않습니다.
  • 첫 그리기는 웹·앱 같음: 앱 판별은 마운트 뒤에만 보고, 첫 그리기·안내 영역은 웹과 같으므로 수화 불일치와 깜빡임이 없습니다.
