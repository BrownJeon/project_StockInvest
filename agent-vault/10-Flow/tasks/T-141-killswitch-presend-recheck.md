**킬스위치는 사용자의 비상 제동이다.** 그런데 `submitOrder` 는 그것을 **3단계에서 한 번만** 확인하고, 실제 송신은 **8단계**다. 그 사이에 `await` 가 여러 번 들어간다 — 그중 하나가 **토큰 발급 대기**이고, T-138 이 그 대기를 최대 약 180초까지 **넓힐 수 있다**(T-138 QA F-1 실측 94.8초·이론 180초).

**즉 사용자가 킬스위치를 내려도, 이미 3단계를 지난 주문은 최대 3분 뒤에 그대로 나갈 수 있다.**

## 하지 않는 것

- **`realSubmit` 안(거래소 어댑터)에는 손대지 않는다.** 토큰 획득이 5~6 단계에서 끝나므로 8a 재확인으로 실효가 있다. 어댑터에 "송신 직전 콜백" 을 뚫는 것은 침습적이고, 주문 어댑터를 건드리는 위험이 이득보다 크다.
- **잔여 틈을 숨기지 않는다**: 8a 와 실제 HTTP 송신 사이에도 `realSubmit` 안의 캐시 읽기·스로틀 대기가 있다. 토큰이 그 짧은 사이에 죽으면 다시 발급 대기가 생길 수 있다. **T-072 F-15 가 검증 관문에 대해 수용한 것과 같은 잔여 틈**이고, 완전히 없애려면 어댑터 변경이 필요하다 → 후속 후보 1.
- 킬스위치 자체의 판정 로직(`kill-switch.ts`)은 바꾸지 않는다.

## Leader 정리 — QA FAIL(리더 에스컬레이션) 접수

QA 판정은 **FAIL**이고 사유는 「변경 자체에는 결함·회귀 없음, 그러나 **계약상 Critical 인 킬스위치 우회 2건(F-1·F-2)이 재현**돼 통과를 선언할 수 없다」다. `status` 를 `ready-to-deploy` 로 둔 것도 QA 가 지적해 **`blocked-user-decision`** 으로 고쳤다.

### 변경 자체는 깨끗하다 (QA 독립 확인)

코드 변경은 `if (await isKillSwitchActive()) { markBlocked; return }` 한 블록뿐이고(`dry-run.ts:268-271`), `realSubmit` 호출을 늘리지 않으며 `markBlocked` 가 실패해도 `realSubmit` 0회·`status=failed`·`outcomeUnknown` 없음이다. 전체 jest **363스위트 10400건 통과·실패 0**, 변이 **15종 중 14종 탐지**(생존 1종은 동등 변이), 감사자가 살려 둔 M4·M8 도 이제 잡힌다.

### 🔴 QA 가 밝힌 중요한 사실 — 지금은 실주문이 나가지 않는다

운영은 **`system_config.safety_dry_run = true`**(10-30 갱신)이고 **14일간 주문 1건(dry_run)** 뿐이다 `[확실]`. 그래서 F-1·F-2 우회가 **현재 실주문을 내지는 않는다.** 다만 **실매매 재개 전에** 결정이 필요하다 — DRY_RUN 을 끄는 순간 둘 다 살아난다.

### F-1 — QA 가 재현했고 Critical 로 분류했다

토큰 대기가 `realSubmit` 안에 있을 때 킬스위치를 ON 으로 바꿔도 **송신됐다**(sent=1). 같은 대기가 5~6단계 안이면 막힌다. **캐시 적중률은 운영 데이터로 측정 불가(NOT_VERIFIED)**.

- **내 (a) 기각 근거를 QA 가 정정했다** — 토큰 선확보를 넣으면 「수십 스위트」가 아니라 **5개 파일 81건**이 깨진다(원인 `KIS_APP_KEY not set`). 수치는 내가 과장했고, **기각 결론 자체는 맞다**고 QA 가 확인했다.
- QA 판단: 「평시 창이 짧아 수용 근거는 타당하다. 하지만 **수용은 사용자가 해야 한다** — QA 는 Critical 잔존 상태에서 통과를 선언할 수 없다.」 → 사용자에게 올린다.

### 🔴 F-2 — QA 가 감사자도 못 본 경로를 찾았고, 「연기는 맞지 않다」고 반대했다

- 송신되는 경로 **4가지**: (A) 읽기 예외 · **(B) DB 값이 JSON 이 아님** · (D) 재확인 읽기 실패 · **(G) 재확인 값이 JSON 이 아님**. **B·G 는 감사자가 보지 않았다.**
- 원인: `JSON.parse` 가 던지면 `catch` 로 빠져 env 로 간다 → 미설정이면 `false`. **그래서 파일 주석의 「해석 불가 → 활성」과 실제 동작이 다르다** — 코드가 **자기 문서를 지키지 못하고 있다.**
- **QA 의 반대 의견(받아들인다)**: 「이 task 의 목적이 킬스위치 제동 보장인데 F-2 가 같은 제동을 무력화한다. **파싱 실패 분기는 트레이드오프 없이 바로 고칠 수 있다.** 『DB 부분 장애에 주문 전면 중단』 우려는 작다 — 2단계 `INSERT INTO orders` 가 같은 DB 에 쓰므로 DB 가 아프면 주문은 그 단계에서 실패한다`[가능성 높음]`. **DB 읽기 오류 분기만** 사용자 결정 사항이다.」
- 즉 F-2 는 **두 조각**이다: ① **파싱 실패 → 활성**(문서가 이미 그렇게 적고 있다. 트레이드오프 없음) ② **읽기 오류 → 활성?**(트레이드오프 있음 — 사용자 결정).

### 사용자에게 올리는 결정 2건

1. **F-2 ① 파싱 실패 분기를 지금 고칠지** — 권고: **고친다.** 코드가 자기 주석을 지키지 못하는 버그이고, T-141 의 목적(제동 보장)과 같은 대상이다. `kill-switch.ts` 를 열므로 T-141 범위를 넓히고 **감사부터 다시 돈다.**
2. **F-1 잔여 창을 수용하고 T-141 을 「부분 해소」로 배포할지** — 권고: **지금 배포하지 않는다.** 운영이 DRY_RUN 이라 급하지 않고, F-2 ①을 함께 고쳐 한 번에 감사받는 편이 낫다. 그리고 serve-stale(T-138 후속 1)이 F-1 을 주문 게이트를 건드리지 않고 없앤다.

### 배포 후 확인 (QA 최종본)

이 변경은 **차단이 늘어나는 방향**이다. `kill_switch` 차단 기준선은 **현재 0건**이고, **DRY_RUN 에서는 8a-0 에 닿지 않으므로 배포 후에도 변하면 안 된다**(변하면 뭔가 잘못된 것). 명령은 `## QA` 절에 있다.
