## Leader 기본 방침

1. **데모 게이트**: WP-A 는 로그인 화면에 새 상태가 생기므로 `delta` 데모를 거친다(judge 접수 `demo_pref=require` → DM-user-required, 프로젝트 금기 "UI 데모 승인 없이 화면 즉흥 구현 금지"). 승인 전에는 화면 코드를 쓰지 않는다. M2 자체는 새 화면이 없다(링크가 기존 화면을 연다).
2. **WP-A 와 WP-M2 는 따로 낸다**: WP-A 는 웹 배포만으로 끝나고(되돌리기 쉬움), WP-M2 는 APK 재설치가 필요하다. 한 push·한 APK 에 묶지 않는다.
3. **판단은 화면 표시용**이다(`window.Capacitor` 는 누구나 흉내 낸다) — 서버 권한 판단에 쓰지 않는다. 모르는 값(빌드 번호를 못 읽음)으로는 막지 않는다("업데이트를 강제하지 않는다" 기존 원칙).
4. 이메일 로그인은 옛 앱에서도 된다 — 게이트는 Google 버튼만 대신하고 이메일 폼은 그대로 둔다.
5. 사용자 몫(AI 가 대신할 수 없음): 데모 승인, **M2-0 실기기 시험 승인·수행**(텔레그램 승인 점검 메시지 발송은 외부 발송이라 사용자 승인), APK 재설치, 실기기 확인. push·APK 공개·`app_release` INSERT 는 단계마다 사용자 승인.
6. **수익 연결(제1원칙)**: WP-A 는 앱 사용자가 로그인에서 막히지 않게 하는 방어(직접 수익 아님). M2 는 승인 요청을 앱으로 바로 열어 승인 지연·진입 놓침을 줄이는 쪽이라 병목(시그널→체결 전환)에 M1·WP-A 보다 가깝다. 다만 시그널 1,286건 중 집행 0·체결 매수 0 이라 전환이 막힌 상태이고 킬스위치 ON·전략 검증 전이라 **M2 의 실효는 당분간 제한적**이다 — M2 착수 시점은 통합 실행 절차(S00~S09)와 견줘 사용자가 정한다(아래 결정 요청 2).

## 설계(초안 — Developer·designer 착수 전 Leader 작성)

### WP-A 버전 게이트
- **필요 최소 build 표**(한 곳): 예 `APP_FEATURE_MIN_BUILD = { googleLogin: 2 }` — 새 네이티브 의존 기능이 생길 때마다 한 줄 추가. 헬퍼 `appMeetsBuild(minBuild)`: 앱이 아니거나(웹) 빌드를 못 읽으면 **true**(막지 않음), 읽었고 minBuild 미만이면 false.
- **적용**: `OAuthButtons`(`appLogin`) 에서 앱이고 build<2 이면 Google 버튼 대신 "업데이트 필요" 안내(새 버전 받기 링크 = 같은 출처 `/app/download/latest.apk`, 공개 경로). 이메일 폼 그대로. 웹·1.0.1 이상은 변화 없음.
- **확인할 사실**(Developer): 옛 APK(1.0.0)에 `App` 플러그인이 있어 `getInfo()` 로 build 를 읽을 수 있는가(`/home/brownjeon/apps/stockinvest/shared/app-releases/stockinvest-1.0.0.apk` 안 플러그인 목록·`capacitor.plugins.json` 로 확인 — 읽기 전용). 못 읽으면 게이트가 작동하지 않으므로 대안(서버가 UA·헤더로 앱 빌드를 알 수 있는지 등) 설계.
- 일반화 규칙을 절차서 `docs/mobile-app-procedure.md`·`docs/deploy-order.md` 「앱(APK) 배포」에 한 단락으로: "네이티브에 기대는 화면은 웹 배포 전에 게이트를 둔다."
- 시험: 순수 로직 jest(표·헬퍼·경계값: 앱 아님/빌드 모름/1/2/3), 화면 렌더(앱 build 1 → 안내·Google 버튼 없음·이메일 폼 있음 / build 2 → 버튼 있음 / 웹 → 버튼 있음).

### WP-M2 (WP-A 승인·배포 뒤 착수, 사용자 결정 필요)
- 절차서 M2 2-0~2-3. **M2-0 시험의 현실적 한계**: 현재 APK(1.0.0/1.0.1)에는 `https` 링크 수신 설정이 없어 텔레그램 링크로는 앱이 열릴 수 없다 — 시험 자체가 `assetlinks.json` 서빙 + Manifest `autoVerify` 가 든 시험 APK(1.1.0, versionCode 3)를 요구한다. 즉 M2-0 과 2-1 은 사실상 같은 빌드다. 제안: (1) 먼저 **코드 없는 예측 시험**(사용자 폰) — 텔레그램 설정 › 채팅 설정 › "인앱 브라우저" 켜짐/꺼짐에서 다른 앱의 확인된 앱 링크(예: 이미 설치한 앱의 공유 링크)를 눌러 앱이 열리는지 본다(1분) (2) 가능성이 있으면 `assetlinks.json`(middleware `PUBLIC_EXACT` 정확 일치 1개, 시험 "그 외 경로는 여전히 인증")+Manifest+`appUrlOpen` 핸들러를 만들고 APK 1.1.0 으로 승인 점검 메시지 링크를 시험 (3) 텔레그램이 가로채면 M2 를 접고 보고(절차서: 대안 없음).
- `assetlinks.json` 서빙: **middleware 방식**(코드 안, SAFETY — Reviewer 필수·정확 일치 1개씩) vs **nginx**(HOME-SERVER, sudo — 이 task 범위 밖). 권고: middleware(정확 일치 1줄).
