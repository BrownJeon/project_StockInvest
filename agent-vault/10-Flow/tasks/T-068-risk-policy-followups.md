# T-068 — 리스크 정책 후속

> 불변 원칙(사용자): 이 프로젝트는 수익을 내기 위해 존재한다. 이 작업은 *손실을 일찍 알아차리고(알림), 정책 표시를 사실에 맞추는(현금 하한·분할)* 일이다. 설계 정본: [[T-064-profit-engine-design]] §7·§7.6, 선행: [[T-066-risk-policy-settings]].

## 요구 (사용자 원문, 2026-10-22)

1. "현금 하한 규칙은 권고대로 처리"
2. "분할 횟수는 현재 시그널에서는 4분할까지 가능하도록 되어있어서 4회로해서 실제 집행하는 횟수도 맞춰줘"
3. "손절가도달시 텔레그램으로 알림 수신하도록 해줘."

## 사실 (Leader 가 코드·DB 로 확인, 2026-10-22 18:00)

- 현금 하한 10% 는 `trading-strategy.md` §5 의 문서 정책이고 **코드로 집행되지 않는다**. 권고(사용자 채택)는 *규칙 없음 + 현금 비중 정보 표시*.
- "4분할" 의 출처: 시나리오 빌더(`ScenarioBuilder.tsx`·`ScenarioDetail.tsx`)가 분할을 `[1,2,3,4]` 로만 고르게 한다. 서버(`scenario-confirm-fields.ts`)는 `splits` 정수 ≥ 1 만 검사하고 상한이 없다.
- 집행 쪽 분할 장치: `maxPositionsPerSymbol`(같은 종목 24시간 내 BUY 시그널 수 한도, `portfolio-stability.ts`, AI 필터 프롬프트 `ai-filter.ts` 의 "종목당 최대 동시 진입"). 코드 기본값 **5**(`style.ts:95`), 범위 [1,20], DB 덮어쓰기 `style_default_maxPositionsPerSymbol` 는 **없음** → 지금 집행값은 5.
- 보유기간 초과 텔레그램 알림 선례: `cron/holding-checker`(1분 틱, `sendAlert` from `@/lib/notify`, 중복 방지로 상태 초기화). 텔레그램 채널·발송 정상(`notify_channel="telegram"`, 부팅 알림 수신 확인).
- `risk_policy` 키는 운영에 이미 있다(version 1, 손절폭 3·한도 2·평균단가 기준, 사용자 저장). 보유 5종목 모두 현재 예상 손절가 **아래** (알림이 켜지면 첫 평가에서 모두 '이미 아래').
- 해외(미국) 수수료는 매수·매도 각 0.25% (AI 필터 프롬프트에도 반영돼 있음).

## 작업 묶음

### WP-A — 화면 변경 (데모 게이트 대상)
- **현금 하한 → 정보 표시**: 정책표의 '현금 하한 10% (문서 정책) · 미달' 행을 **'현금 비중 (정보 표시, 하한 없음)'** 으로 바꾼다. 현재 상태 열에는 현금 비중 %만 보여 주고 경고(`!`·미달)를 쓰지 않는다. '정책과 다른 현재 상태' 목록과 요약 행의 '확인 필요 n건' 에서 현금 항목을 뺀다. `defaults.ts` 의 `cashFloorPct` 는 규칙 값이 아니므로 제거(또는 정보용 null).
- **분할 횟수 4**: 정책표 '분할 매수 최대 3회 (40/30/30)' → **'분할 매수 최대 4회'**, 출처 '사용자 확정'. 비율은 *구간을 균등하게 나눠 각 구간에 같은 금액*(실제 `calcSplitSlices` 동작을 코드로 확인해 그대로 표기; 확인 안 되면 비율 표기를 뺀다). 현재 상태 열에는 **집행 중 한도(= WP-B 이후 4)** 를 같은 값으로 보여 준다 — 읽는 방식은 아래 WP-B 와 함께 Developer 가 결정(DB 덮어쓰기까지 반영한 실효값을 읽기 전용으로).
- **안내 문구**: 지금 화면의 '저장해도 매도 주문·알림은 만들지 않습니다' 는 WP-C 이후 거짓이 되므로 **'저장해도 매도 주문은 만들지 않습니다. 손절가 도달 시 텔레그램 알림만 보냅니다'** 로, 배지 '표시·위험 계산 전용' 은 **'표시·위험 계산·알림 (주문·매도 없음)'** 으로 바꾼다.
- 승인 데모: 기존 v3 에 대한 *delta* 데모 v4 를 designer 가 만들어 사용자 승인을 받은 뒤에만 화면 코드를 쓴다.

### WP-B — 집행 분할 한도 5 → 4 (안전 경로: `src/lib/strategy/` → SAFETY_PATHS)
- `style.ts` 의 `maxPositionsPerSymbol` 기본값 5 → **4**. 영향 범위(`portfolio-stability.ts` 거절 사유 문구, `ai-filter.ts` 프롬프트의 '종목당 최대 동시 진입', 시험 기댓값)를 모두 확인해 맞춘다. DB 덮어쓰기 키가 새로 생기면 그 값이 우선하는 기존 동작은 유지.
- 효과(정정 10-22 18:4x): `portfolio-stability.ts` 는 `market !== 'domestic'` 이면 즉시 통과하고 최근 24시간 동일 종목 매수 *주문*(filled·accepted·partially_filled)을 세며 호출자는 `engine.ts` 한 곳이다. 따라서 5→4 는 **국내 룰 엔진 경로에만** 효과가 있고 미국·시나리오 확정 경로의 분할은 막지 못한다(독립 검토 R-04, Leader 코드 재확인). 처음에 쓴 "시나리오 빌더의 1~4분할과 같은 크기가 된다"는 과장이었다.
- **범위 추가(10-22 18:4x, 사용자 요청 '실제 집행하는 횟수도 4회로 맞춰줘' 충족용)**: `src/lib/safety/scenario-confirm-fields.ts` 에 `MAX_SCENARIO_SPLITS = 4` 를 두고 `splits`·`manualSlices.length` 가 4 를 넘으면 확정 요청을 거부한다(현재는 정수 ≥1 외 상한 없음). UI(1~4분할)는 변경 없음. `src/lib/safety/` 는 SAFETY_PATHS → Reviewer 범위에 포함. 여러 요청·여러 날에 걸친 *누적* 분할 게이트는 없고 안전 경로 설계가 필요해 T-064 D17(사용자 결정)로 올린다.

### WP-C — 손절가 도달 텔레그램 알림 (안전 경로: `src/app/api/cron/`·`scripts/cron-runner.sh` → SAFETY_PATHS)
- 목적: 보유 종목의 현재가가 **예상 손절가**(= 기준가 × (1 − 손절폭), 사용자 저장 정책 `risk_policy`) 에 닿거나 그 아래로 내려가면 텔레그램으로 알린다. **알림만** — 주문·매도·시그널을 만들지 않는다.
- 구성:
  - 순수 모듈 `src/lib/risk/stop-alert.ts`: 입력(보유 목록·가격·정책·이전 상태·시각)을 받아 `{다음 상태, 보낼 알림 목록}` 을 돌려준다. I/O·notify·exchanges import **금지**(순수). 예상 손절가 계산은 T-066 의 `compute.ts` 와 **같은 정의**(한 곳)를 쓴다.
  - cron 라우트 `src/app/api/cron/stop-alert/route.ts`(POST, `checkCronAuth`): `risk_policy`·`position_state`(평균단가·고점·수량)를 읽고, **장이 열린 시장의 보유 종목만** 거래소 시세(`getTicker`)로 현재가를 얻어 순수 모듈에 넘기고, 결과를 `sendAlert`(@/lib/notify)로 보낸 뒤 상태를 저장한다.
  - `scripts/cron-runner.sh`: 1분 틱에 `stop-alert` 호출 한 줄 추가. 러너는 동기 루프라 하트비트 보호(`CALL_MAX_TIME` 등 기존 패턴)를 반드시 쓴다.
  - 상태 저장: `system_config` 키 `risk_stop_alert_state`(JSON; 종목별 `{state:'above'|'below', since, lastAlertAt}` + 정책 버전 + 일일 발송 수). DDL 없음.
  - 켜고 끄기: `system_config` 키 `risk_stop_alert_enabled`(없음 = 켜짐, JSON `false` = 끔). 화면 토글은 이번 범위 밖(후속 데모 필요).
- 알림 규칙:
  1. **교차**: 직전 평가에서 위(또는 상태 없음 아님)였다가 이번에 현재가 ≤ 예상 손절가가 되면 종목별 1건 발송.
  2. **최초 요약**: 상태가 없는 종목이 이미 손절가 아래이면 종목마다 보내지 않고 **시장별 1건의 요약**(예: "현재 N종목이 이미 예상 손절가 아래입니다") 만 보낸 뒤 상태를 'below' 로 기록한다.
  3. **재무장**: 아래였던 종목이 손절가 대비 **+0.5% 이상 위**로 올라와 2회 연속 확인되면 'above' 로 되돌린다(회복 알림은 보내지 않는다). 같은 종목 재알림 쿨다운 60분. 일일 최대 20건(초과분은 로그만).
  4. **정책 변경**: `risk_policy.version` 이 바뀐 첫 평가는 알림 없이 상태만 새로 맞춘다(사용자가 방금 바꾼 값이므로).
  5. **정책 없음/손상·시세 실패·장 마감**: 알림 없음, 상태 불변, 로그만.
  6. **발송 실패**: 상태를 '알림함' 으로 바꾸지 않아 다음 틱에 재시도(최대 3회, 이후 60분 대기). 실패가 거래·cron 에 영향을 주면 안 된다.
- 메시지(한국어, 간결): 제목 '🔻 손절가 도달 — {종목 라벨}'. 본문: 현재가 / 예상 손절가(기준·손절폭) / 평균단가 / 평가손익률 / 손절 시 손익 금액(정의대로) / '주문은 자동으로 나가지 않습니다. 직접 판단하세요.'
- 격리: 거래소는 `getTicker` 만(주문·잔고 쓰기 금지), 주문·시그널·`position_state` **쓰기 금지**, KIS 호출 상한(보유 ≤10종목/틱, 장 열린 시장만). 기존 격리 시험을 이 경로의 *명시적 예외*(cron 라우트 → risk 방향 1건)로 갱신하되 순수 모듈은 여전히 notify/exchanges import 0 을 단언.
- 시험: 순수 모듈 표 시험(교차·최초 요약·재무장·쿨다운·정책 변경 재설정·시세 없음·일일 상한), 라우트 시험(인증·꺼짐 플래그·발송 실패 시 상태 불변·상태 저장·장 마감 시 KIS 호출 0), 격리 시험 갱신, cron-runner 시험(하트비트 보호).
