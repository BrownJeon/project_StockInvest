# T-052 — 사용자 시나리오 확정 경로 하드닝 (T-050 배포의 선행 조건)

## 배경

T-050(만료 시각 UTC 버그)의 Codex C2 검토가 **기존 구조 결함 2건**(high)을 짚었고 Leader 가 코드로 모두 확인했다([[T-050-custom-signal-expiry-timezone]] "Codex C2"). 이 결함들은 15시간 만료가 우연히 완충하던 것이라, T-050 이 만료를 24시간으로 정상화하면 노출 구간이 넓어진다 → **T-050 배포는 이 task 뒤**로 보류했다.

`POST /api/signals/custom/confirm` 은 사용자 시나리오를 **사람 승인 없이 곧바로 `approved_pending_entry`**(진입 감시)로 넣는다(T-029). 거의 쓰이지 않는 경로(`scenario_source='user'` 전체 9행, 마지막 09-03)이나, 쓰이면 실주문으로 이어진다.

## 결함

### D-1. 서버 멱등성 없음 (중복 확정 → 실주문 중복)

`route.ts:168-198`: signal INSERT 가 무조건 실행되고 원본 시그널 소비(`UPDATE … WHERE id=? AND status IN (…)`)는 모든 INSERT 뒤다. 같은 시나리오를 두 번 확정하면(동시 요청·네트워크 재시도·탭 두 개·성공 후 리다이렉트 1.2~1.8초 사이 재클릭) 서로 다른 signal 이 둘 생기고 `entry-watcher` 의 선점(T-043)은 **개별 signal ID 단위**라 둘 다 각각 선점돼 실주문이 두 번 나갈 수 있다. 유니크 인덱스 `uq_signals_scenario_card` 는 `valid_from` 이 NULL 인 `user` 행에 적용되지 않는다. UI(`ScenarioDetail.tsx`·`recommend/build/page.tsx`)는 제출 중 버튼을 비활성화하지만 서버 방어가 아니다.

### D-2. `holding_deadline` 주문 전 검사 없음

`entry-watcher/route.ts:49`(`resolveHoldingDeadline`)는 **주문 뒤** `position_state` 기록에만 쓰인다. 보유 마감이 이미 지난 시나리오도 `expires_at` 전이면 선점·주문을 통과한다. 청산 엔진이 꺼져 있어(`exit_engine_enabled=false`) 자동 정리가 없고 `holding-checker` 가 "보유기간 초과" 경고만 보낸다.

## 설계 선택지 (사용자 결정 필요)

**D-1 멱등성**
- (a) `sourceSignalId` 경로: 트랜잭션 안에서 원본을 **조건부 선점**(`UPDATE … SET status='approved' WHERE id=? AND status IN (…)` 의 `affectedRows===1`)한 뒤에만 INSERT, 분할 INSERT 와 원본 소비를 한 트랜잭션으로.
- (b) 직접 작성 경로(`sourceSignalId` 없음): 클라이언트가 만든 **멱등 키**(UUID)를 요청에 싣고 DB UNIQUE 제약(예: 신규 컬럼 또는 `indicators` JSON 의 `group_id` 를 클라이언트가 지정 + 생성 컬럼 유니크) → 스키마 변경이면 마이그레이션 = 사용자 승인 사항.
- (c) 최소안: 같은 (symbol, side, 가격 구간) 의 미소비 `user` 시나리오가 이미 `approved_pending_entry` 이면 거절 — 스키마 변경 없이 가능, 정당한 재등록을 막는지 검토 필요.

**D-2 보유 마감일**
- (a) 확정 시 `expires_at = min(지금+24h, holding_deadline 당일 23:59:59 KST)` — 이미 지난 마감이면 확정을 400 으로 거절할지(과도차단 위험: T-029 회귀 방지 원칙) 만료로 통과시킬지 결정 필요.
- (b) `entry-watcher` 선점 전에 마감 지난 행을 `expired` 로 원자 전환 — 주문 경로 수정(감사 범위 큼, 모든 시나리오에 적용).
- (c) 현 상태 유지 + 경고만 — 청산 엔진이 OFF 인 동안은 비권고.
