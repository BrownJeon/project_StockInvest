## 화면과 기록 설계

- 분석 → 데이터 상태의 기존 화면에서 홈 알림이 당일 이상 목록으로 바로 이동한다. 2026-11-07 사용자 수정 요청에 따라 기존 홈과 분석의 메뉴, 요소와 순서를 보존한다. 데이터 상태의 ‘가동률’과 ‘원천별 신선도’ 뒤에 새 내역 섹션을 추가하고 홈 알림 링크에서 그 위치를 가리킨다. 데이터 원천 문제와 작업 실행 문제를 구분하고 각 항목에 시각, 사용자용 사유, 근거 또는 기록 없음, 다음 정상 실행 정보를 둔다. 홈과 같은 KST 날짜·집계 범위를 사용한다.
- 과거 `HTTP=000` 행은 원인 코드가 없으면 확인된 수준까지만 표시한다. 앞으로는 러너에서 curl 종료 코드와 소요 시간에 기반한 제한된 분류를 기록한다. 예를 들어 7은 연결 실패, 28은 제한 시간 초과, 52·56은 응답 없음·수신 실패다. 기존 v1 스풀을 계속 수신하고 신규 포맷의 제한된 숫자 필드를 검증한다. 새 송신 형식보다 수신 호환을 먼저 확보한다. 기존 `error_code`와 시작·종료 시각을 우선 활용한다.
- 서버가 응답하기 전에 호출자가 끊긴 경우, 직접 원인을 분류하려면 서버 단계 기록이 별도로 필요하다. 요청별 상관 ID로 러너와 서버 기록을 연결할 수 있는 경우에만 서버 내부 원인을 확정 표시한다. 배포 시간대와만 일치하면 관련 정황으로 구분한다. 화면 API는 허용된 사유·상태만 전달하고 로그 본문이나 인증 정보는 포함하지 않는다.
- 롤업 잡은 이후 정상 응답의 시각을 개별 행에서 확인할 수 없는 경우가 있다. 최신 시각이 관측된 경우와 회복 기록이 없는 경우를 구분한다.

## 서버 구현 및 승인 기록 차단

- 사용자 v2 승인은 같은 세션의 발화 훅에 수집됐다. `approve-codex-context`는 대화 기록에서 인식하지 못한 `additional_content.codex_apps_selected_page_part_1_of_1` 종류의 `harness` 부가 항목이 같이 들어 있어 거부했다. 설치본 검증은 실패했고 해당 종류를 `harness`로만 인식하도록 한 메모리상의 복사본에서는 원본 대화·검토 영수증·해시·사용자 발화 대조가 통과했다. 공용 도구와 증거 파일에는 쓰지 않았다. `check`가 계속 BLOCKED라 화면 경로를 편집하지 않았다.
- 기존 v1 스풀에서 HTTP 응답이 없는 경우 curl 종료 코드만 기록한다. 이미 저장된 `HTTP=000`은 상세 원인을 추정하지 않는다. 완전한 성공 응답을 확인한 일반 행과 시간대 요약에는 `lastOkStartMs`를 기록한다. 요약 시각은 확인된 후속 실행 시각의 한 사례이며 최초 후속 시각을 뜻하지 않는다. 세 분 단위 잡은 최대 2,049바이트를 250ms 내에서 검사하고 원문 없이 성공 표시만 저장한다. 제한·미지원·구버전 기록은 미확인으로 남긴다. 구버전 기록기의 롤업 갱신은 새 키를 제거할 수 있으므로 혼합 버전 전환·롤백은 별도 검증 대상이다.
- 분석 데이터 API는 홈과 같은 KST 날짜 및 최대 20개 실행 기록 기준을 재사용한다. 기존 7개 원천과 실행 이상을 분리하고, 제한된 사유와 같은 작업·시장의 검증된 이후 정상 실행만 반환한다. 작업 성공은 해당 라우트가 기록한 결과 범위이며 예를 들어 스냅샷 성공이 별도 drawdown 계산 성공을 보장하지 않는다. `route`는 검증 마커가 있으면 읽도록 했으며 현재 마커를 쓰는 경로는 러너다.
- Ubuntu의 운영 릴리스 기반 격리 사본에서 최종 관련 Jest 236건과 타입 검사, 러너 J3/J5/J8 38건을 통과했다. 일회용 MariaDB 통합 시험 32건과 새 진단 SQL·롤업 대조 3건도 통과했다. 별도 route fixture에서 검증 마커가 있는 후속 행만 인정됐다. Node 기동 지연·부재 모의에서 v1 줄은 유지했고 성공 근거는 생기지 않았다. 지연 모의는 254ms였다. 실제 운영 응답·UI·배포는 검증 범위 밖이다.
