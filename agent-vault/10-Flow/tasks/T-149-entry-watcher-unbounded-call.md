## 실측 ③ 주문 경로 겹침은 이미 DB 로 막혀 있다 — 인수 전제 2가 틀렸다 [확실]

브리핑이 인용한 `order-sync.ts:1226-1227` 의 `FOR UPDATE`·`GET_LOCK()` 기각은
**`recordSettledFill`(브로커 체결 내역을 `executions` 에 적는 사후 정산 경로)** 에 대한 판단이다.
주문을 **내는** 경로의 판단이 아니다. 주문 경로에는 이미 두 겹의 DB 장치가 있다.

### ⓐ 시그널당 이중 주문 — 조건부 UPDATE 선점 (T-043)

`src/lib/signals/entry-claim.ts:31-38`:

```sql
UPDATE signals SET status='executing', updated_at=NOW()
  WHERE id=? AND status='approved_pending_entry' AND (expires_at IS NULL OR expires_at > NOW())
```

`affectedRows === 1` 인 쪽만 `submitOrder` 를 부른다. entry-watcher 가 동시에 둘 돌아도
**같은 시그널에 주문이 두 번 나갈 수 없다** — 진 쪽은 `claim_lost`. 러너의 직렬화와 무관하게 성립한다.

### ⓑ 일일 누적 한도 — check-then-act 가 아니라 **예약 후 검사** (T-081 WP-B)

`src/lib/safety/dry-run.ts` 의 순서가 결정적이다:

- 2단계(160행): `INSERT INTO orders … status='pending'` ← **한도 검사보다 먼저** 행을 만든다(예약)
- 6단계(216행): `checkDailyMax(reqWithKrw, effDailyMax, orderId)`
- `src/lib/safety/order-limits.ts:245-253`: 오늘 매수 합산에서 `NOT (status='pending' AND id=?)` 로
  **자기 행만** 뺀다 → **다른 주문의 `pending` 은 합산된다**

dry-run.ts 주석이 직접 그렇게 적어 뒀다: *"다른 주문의 `pending`(송신 중)은 합산 → 동시 매수 경합 차단"*.
두 호출이 동시에 와도 각자 자기 행을 먼저 박고 서로의 행을 보므로 한도를 함께 넘지 못한다.

### 잔여 — 안전장치가 아닌 것

현금 사전 점검(T-051 `judgeEntryCash`)은 동시 실행 시 같은 잔고를 두 번 보고 둘 다 통과할 수 있다.
다만 이것은 브로커 거부를 줄이려는 **사전 점검**이고, 권위 있는 상한(1회·일일)은 위처럼 DB 로 예약된다.
프로세스 로컬 스로틀(현금 부족 알림·`sendAlertThrottled`)도 중복 알림이 가능하지만 주문은 아니다.

**결론: 상한을 붙이는 것이 「주문 경로를 직렬화하는 유일한 장치를 무력화한다」는 전제는 성립하지 않는다.**
단일비행 가드를 상한보다 선행시킬 이유가 없다.

### A. 틀린 근거 2건 — 러너 주석 (가장 중요)

안전 파일 주석의 틀린 제약은 다음 사람이 그것을 **진짜 제약으로 믿고 설계를 포기하게** 만든다. 그래서 문구를 고치는 데 그치지 않고
**되살아나면 시험이 깨지게** 박았다(아래 C).

| # | 틀린 서술 (T-147) | 고친 내용 | 위치 |
|---|---|---|---|
| 1 | 「일일 누적 한도가 check-then-act 라 **무제한 동기 호출이 cron 끼리의 주문 직렬화 장치**」 | 주문 동시 실행은 **DB 가 막는다** — ① `entry-claim.ts` 조건부 UPDATE 선점(T-043) ② `dry-run.ts` 가 송신 전 `orders` 행을 `pending` 으로 **먼저 INSERT** 하고 `order-limits.ts` 합산이 **타 주문 `pending` 포함**(T-081 WP-B) = 예약 후 검사. `order-sync.ts:1226-1227` 의 기각은 **체결 내역 정산**(`recordSettledFill`) 경로 판단이라는 경고를 함께 남겼다. 결론(주문 잡을 티커로 옮기지 않는다)은 유지하고 근거만 ⓐ 서버 처리는 계속 돈다 ⓑ `job_run_log` HTTP 000 오염으로 교체 | alert-ticker 블록 「왜 stop-alert 만」 |
| 2 | 「국내 **150종목** 직렬 평가」 | 종목 수 서술을 지우고 **42~65종목**으로 교체(운영 `pm2-out.log` `ran=` 전체 분포: 43이 99회·51이 62회·65가 30회·63이 12회·64가 9회·49가 3회·42가 2회 — 시장 구분 없는 합계). **왜 긴지는 이 블록에서 단정하지 않고 T-148 로 넘긴다** | 같은 블록 「왜」 |

🔴 **이 항목에서 틀린 근거가 두 번 들어갔다.** 기록해 둔다 — 이 task 자체가 「틀린 근거가 주석에 남는 것」을 고치는
작업이라 같은 실수의 이력이 다음 사람에게 쓸모 있다.

1. **1차(인계 원문 유래).** 인계 메시지에 「회차당 median 279 호출이고 레이트 5 req/s 라 바닥이 약 56초 — 병목은 종목 수가
   아니라 레이트 한도」라고 적혀 있었고, 나는 그것을 **검증 없이 러너 주석으로 옮겼다.** 인계 세션이 뒤에 출처가 자기임을

- `noc()`·`strip_old()`·`strip_new()`·`strip_blk()` 는 모두 끝에 `grep -v '^[[:space:]]*#'` 가 있어 **전행 주석을 전부 제거**한다 → D6·H9·P7·news-split 의 블록 밖 실행 줄 대조는 주석 변경과 무관하다 ✅
- 그런데 **주석을 포함하는 대조가 2곳 있다**: `daily-bars.sh:295`·`job-run-log.sh:395` 의 awk 부분수열 검사(「기준 ref 의 모든 줄이 **주석 포함** 순서대로 남아 있다 = 추가만」).
  - T-147 **블록 안**의 주석 변경은 안전하다(기준 ref 에 그 줄이 없다 — 추가분이다).
  - `:271`(T-112 주석)도 안전하다 — 두 기준 ref(`faf8bc3`·`f218430`)에 그 문구가 **0건**임을 실측했다.
  - `:151`(T-062 주석)은 **두 기준 ref 모두에 1건 있다** → 문구를 고치면 두 대조가 깨진다. 그래서 `no_kf_old`·`no_t147_old` 선례대로 **스트리퍼 `no_t149_old()` 를 두 하네스에 추가**했다(기준 ref 쪽에서 그 1줄만 제거. 접두 `^# (T-062 Codex C2 ②) 해외 post-market` 가 양쪽에서 정확히 1줄만 잡음을 실측). **기준 ref 를 옮기지 않았다.**
- `call()` 본문은 **주석까지 sha256 으로 고정**돼 있다(`daily-bars.sh:297`·`job-run-log.sh:398`) → `call()` 안은 한 글자도 건드리지 않았다. mktemp 한계 기록은 `call_tmp_open` 앞, `# >>> call-body-tmp` 블록 **안**에 뒀다(`no_t135` 가 제거 → 영향 0). J13 의 줄 수 대조는 `cbk`(블록 전체)와 자기정합이라 추가분만큼 양쪽이 같이 늘어난다.
- **레거시 모드에서는 `alert_ticker_alive` 가 호출되지 않는다**(`ALERT_TICKER_ACTIVE=0` 이라 감독 조건이 단축평가) → 옛 하네스 8개는 R-1 코드 변경을 보지 못한다. 런타임 비교(호출 목록·`--max-time`·stdout·하트비트)도 주석과 무관하다.

## R-1 실증 (완료 기준 — 직접 실행)

러너에서 `alert_ticker_alive` 만 떼어 **고치기 전(HEAD)과 고친 뒤**를 같은 입력으로 비교했다(서버, `/tmp/t149-r1-proof.sh`).

| 경우 | 고침 전 | 고침 후 | 기대 |
|---|---|---|---|
| 진짜 직계 자식 | 0 (살아 있음) | **0** | 0 — 방어가 정상 티커를 죽이지 않아야 한다 |
| 살아 있지만 내 자식이 아닌 pid | **0 (살아 있음 — 오판)** | **1 (죽음)** | 1 — R-1 이 지적한 pid 재사용 오판 |
| 빈 PID | 1 | 1 | 1 |
| 없는 pid(4194303) | 1 | 1 | 1 |

파싱을 다시 썼으므로 두 가지를 더 확인했다(`/tmp/t149-r1-parse.sh`):

- **좀비**: 판정 1(죽음) — ② 검사 유지. (실측에서 bash 가 이미 reap 해 `kill -0` 단계에서 걸렀다 — 기존 주석의 측정과 일치.)
- **comm 에 공백·괄호**: `/proc/<pid>/stat` 이 `519760 (t149 we) ird) S 519746 …` 일 때 다시 쓴 파싱 결과 `S 519746` = 참값(awk)과 **일치**. 탐욕 `s/^.*) //` 가 마지막 `)` 까지 올바르게 버린다.

### 🔴 신규 시험이 내 결함 1건을 잡았다 (1차 실행)

1차 하네스 실행에서 alert-ticker 가 **2건 실패**했다. 내가 high_risk_areas 에 적어 둔 바로 그 실패다.

```
FAIL 🔴 E3 기본: 티커를 띄우고 메인 루프는 부르지 않는다 (기대 '1 0', 실제 '1 1')
FAIL 🔴 E3 기본: 티커가 분 경계(:00)에 부른다 (기대 'all-on-boundary', 실제 'n=1 onboundary=0')
```

**원인**: 고아 확인 쪽에서 `BASHPID` 를 `$( )` **안에서** 전개했다.

```bash
opp=$(sed -e 's/^.*) //' "/proc/${BASHPID:-0}/stat" ...)   # ❌
```

명령치환은 **새 프로세스**라 그 안의 `BASHPID` 는 치환 서브셸의 pid 이고, 그 ppid 는 러너가 아니라 **티커 자신**이다.
그래서 `opp != ALERT_TICKER_PARENT_PID` 가 늘 참이 되어 **살아 있는 정상 티커가 첫 회차 호출 뒤 스스로 종료**했고,
감독이 그것을 죽은 것으로 보고 ACTIVE=0 으로 내려 메인 루프가 호출을 이어받았다(그래서 호출자가 `1 1`).

**고침**: `BASHPID` 를 명령치환 **밖에서** 변수에 먼저 담는다.

```bash
mypid="${BASHPID:-0}"
if [ -r "/proc/$mypid/stat" ]; then
  opp=$(sed -e 's/^.*) //' "/proc/$mypid/stat" 2>/dev/null) || opp=""
```

감독 쪽(③)이 `$$` 를 그대로 쓸 수 있는 것은 **`$$` 가 서브셸에서도 최초 셸 pid 를 유지**하기 때문이고 `BASHPID` 는 그렇지 않다 —
감사자가 `$$` 를 권고한 이유가 여기 있었다. 재발 방지로 **「`$( )` 안에 `BASHPID` 가 0건」** 단정을 하네스에 추가했다.

> 기능 영향(배포되었다면): 손절 알림은 **멈추지 않았다**(메인 루프가 fail-open 으로 이어받는다). 대신 T-147 의 목적인
> 「긴 틱에도 분당 알림」이 사라져 알림이 다시 틱에 묶였을 것이다. 안전장치·주문 경로와는 무관하다.

### 2차 실행 — `run_block` 계열 4건이 같은 원인으로 실패 (고침)

재실행에서 하네스 8개는 **762 통과 · 실패 0**, alert-ticker 만 6건 실패했다. E3 실패는 사라졌다(위 `BASHPID` 고침이 맞았다).
새 6건의 원인은 하나였다 — **시험이 `alert_ticker_loop` 를 배경 자식이 아니라 그 셸에서 직접 부른다.**

러너 `scripts/cron-runner.sh:504` 의 `ALERT_TICKER_PARENT_PID=$$` 는 블록 안에 있어, 시험이 블록을 source 하면
**시험 셸 자신의 pid** 가 기록된 부모가 된다. 그 셸에서 루프를 직접 부르면 「내 ppid == 기록된 부모」가 성립할 수 없어
(내 ppid 는 `timeout`) 자식 쪽 대조가 늘 발화해 루프가 즉시 끝났다 → 호출 0회·로그 0줄.

**고침은 시험 쪽**이다(제품 코드를 시험에 맞춰 구부리지 않는다). `run_block` 의 heredoc 과 ⑫ 진짜-오류 경로의 별도
`bash -c` 두 곳에 `ALERT_TICKER_PARENT_PID=$PPID` 를 넣어, **그 셸의 실제 부모**를 기록된 부모로 맞췄다 — 그러면
production 과 같은 의미(「내 부모가 아직 그 부모인가」)가 된다. ④ 부모-사망 시험은 EXTRA 줄에서 다시 대입하므로 그대로 동작한다.

### E3 분 경계 간헐 실패 — 관측 수치와 분류 (판정 근거)

남은 1건은 `E3 기본: 티커가 분 경계(:00)에 부른다` → `n=1 onboundary=0` 이다.

**먼저 범위를 정확히 해 둔다.** E 절의 「호출자는 하나」 불변식을 보는 것은 **다른 단정**
(`E3 기본: 티커를 띄우고 메인 루프는 부르지 않는다` = `after_hc` 가 0)이고 그것은 **통과했다**. 즉 이 실패는
「메인 루프가 같이 불렀다(이중 발송 위험)」가 **아니고**, 「티커가 부른 시각의 초가 `00` 이 아니었다」다.
그래도 닫지 않는 이유는 같다 — 분 경계 정렬이 깨지면 T-147 이 노린 「긴 틱에도 분당 1회」가 흐트러진다.

#### ① 격리 측정 — 조건이 다르므로 이것만으로는 증거가 아니다

`start_real` 설정을 복제해 러너 **1개만** 150초씩 번갈아 돌렸다(`/tmp/t149-e3.sh`, 실제 시계·실제 flock·curl 만 스텁,
종료는 PID 로만).

| | 결과 | 호출 시각 |
|---|---|---|
| 고친 러너 #1 | `n=3 onboundary=3` | 22:47:00 · 22:48:00 · 22:49:00 |
| HEAD 러너 #1 | `n=2 onboundary=2` | 22:50:00 · 22:51:00 |
| 고친 러너 #2 | `n=3 onboundary=3` | 22:52:00 · 22:53:00 · 22:54:00 |
| HEAD 러너 #2 | `n=2 onboundary=2` | 22:55:00 · 22:56:00 |

고친 러너가 **매번 정확히 `:00`** 에 부른다(호출 수 차이는 150초 창의 정렬 차이다).

🔴 **그런데 이 측정은 E3 의 조건이 아니다.** E 절은 `start_real` 러너를 **3개 동시에**(legacy·failopen·normal) 띄우고

#### ② 같은 하네스 조건의 A/B 실패율 (판정 근거는 이쪽)

alert-ticker 하네스를 **그대로** 돌리면서 **러너만** 바꿔 끼워(고친 러너 / HEAD 러너) 각 8회 반복하고
`E3 분 경계` 단정의 실패 횟수를 센다. 진단용 사본은 `trap` 을 고쳐 `normal` 러너의 stop-alert 호출 **시각**을 남긴다
(커밋되는 하네스는 손대지 않는다) — 어긋난 초가 `:01` 급이면 부하 지연, `:37` 급이면 로직 문제로 갈린다.
스크립트 `/tmp/t149-ab.sh`, 결과 `/tmp/t149-ab.out`.

해석 규칙을 **결과를 보기 전에** 적었다(결과를 보고 고르지 않는다):

- **양쪽 비슷** → 내 변경 탓이 아니다. 동시에 **별개의 발견**이다 — 이미 운영에 배포된 T-147 티커(릴리스
  `20261103-202418-17a4257f`)를 지키는 시험이 불안정하다는 뜻이므로, 원인이 하네스 쪽(동시 3러너·실제 시계 의존)인지
  러너 쪽(경계 계산)인지를 어긋난 초로 분류해 적는다.
- **HEAD 0/8, 고친 러너만 실패** → 내 변경 탓이다. 그러면 자식 쪽 ppid 대조의 추가 fork 를 없애거나(아래 대안) 철회한다.
- **원인을 끝까지 규명하지 못하면 「모른다」로 적고 관측 수치를 남긴다.** 「사라졌다」·「환경 탓」으로 닫지 않는다.

#### ②-결과 1차 (러너 sha `cf8315665d43ae13` — `sed` 를 쓰던 판)

```
고친 러너(new): 1 / 8      ← #5 실패. 첫 호출 00:52:01  (경계 +1초)
HEAD  러너(old): 0 / 8
```

**해석: 세 갈래 중 「HEAD 0/N, 고친 러너만 실패」에 해당한다 — 내 변경을 면죄하지 않는다.**

- 1/8 과 0/8 은 통계적으로 갈리지 않는다(미리 적어 둔 한계 그대로). 그래서 「노이즈다」라고 **주장하지 않았다.**
- 어긋난 초가 **+1초**다. 로직 오류라면 임의의 초가 나온다 — 경계 계산이 아니라 **스케줄 지연**이다.
- 기여 메커니즘이 설명된다: 내 변경이 **깨어난 뒤 호출 직전** 경로에 `sed` fork 를 1회 추가했다. 그 자리의 fork 는
  원래 `flock`·`curl` 둘인데 하나가 더 붙으면 `:00` 을 넘길 확률이 올라간다.
- **그래서 노이즈라고 넘기는 대신 메커니즘을 없앴다** — 두 곳(감독·자식) 모두 외부 명령을 쓰지 않는 bash 내장
  `read` + 탐욕 `##` 파라미터 확장으로 바꿨다(위에서 실측 검증해 둔 그 대안). 이제 티커의 「깨어남 → 호출」 경로의
  fork 수가 **HEAD 와 같다**(블록 실행 줄에 `sed`·`awk`·`cut` 0건을 하네스가 고정한다).

> 부수 관측(진단 사본의 시각 덤프에서): 모든 회차의 덤프에 `:30`·`:51` 같은 **경계 밖 호출이 섞여 있는데 대부분 PASS** 다.
> E3 단정은 `sleep 80` 직후에 평가되고 내 덤프는 하네스 **종료 시점**에 뜨기 때문이다 — 그 뒤 E 절 후반 시험이 티커를 죽여
> 메인 루프가 인수하면(fallback) 호출이 틱 주기(경계와 무관)로 찍힌다. 즉 덤프의 경계 밖 시각은 결함이 아니라
> **내 진단 도구의 범위 문제**다. 판정에 쓴 것은 하네스 자신의 단정 결과뿐이다.

#### ②-결과 2차 (러너 sha `e15c5a44ccd92388` — fork 없는 판)

같은 스크립트·같은 조건(`/tmp/t149-ab.sh 8`, 하네스 sha `32b94d29f0bfac08` 양쪽 동일)으로 재실행:

```
고친 러너(new): 0 / 8      01:17:00 · 01:22:00 · 01:27:00 · 01:33:00 · 01:38:00 · 01:43:00 · 01:49:00 · 01:54:00
HEAD  러너(old): 0 / 8      01:19:00 · 01:25:00 · 01:30:00 · 01:35:00 · 01:41:00 · 01:46:00 · 01:51:00 · 01:57:00
```

**두 라운드를 합친 관측**:

| 러너 | E3 분 경계 실패 / 시도 |
|---|---|
| HEAD (`78212d78`) | **0 / 16** |
| 고친 러너 — `sed` 판 (`cf831566`) | **1 / 8** |
| 고친 러너 — fork 없는 판 (`e15c5a44`) | **0 / 8** |

fork 를 없앤 뒤 **HEAD 와 동률(0)** 이다. `sed` 판의 1건과 fork 제거 후의 0건은 「호출 직전 fork 가 기여했다」는 설명과
방향이 일치하고, 어긋난 초가 **+1초**였다는 점도 같은 방향이다.

> ⚠ **이 증거의 한계를 분명히 적는다.** 8회씩으로는 1/8 과 0/8 이 통계적으로 갈리지 않는다. 즉 「fork 가 원인임을
> 입증했다」가 아니라 **「원인으로 의심되는 유일한 메커니즘을 제거했고, 제거 후 HEAD 와 동률이 되었다」**가 내가 말할 수 있는
> 전부다. fork 제거 자체는 그 가설이 틀렸더라도 손해가 없다(외부 명령 2개를 bash 내장으로 바꾼 것이고 동작은 실측으로 동일).
> 더 센 증거가 필요하면 같은 스크립트로 `N` 을 올려 돌릴 수 있다(1회 약 165초 × 2N).

**별개의 발견 — 기록해 둔다**: HEAD 가 0/16 이므로 「이미 배포된 T-147 티커를 지키는 시험이 원래 불안정하다」는 쪽은
**이번 관측으로는 뒷받침되지 않는다.** 다만 E 절은 `start_real` 러너 3개를 동시에 띄우고 실제 시계·실제 `flock` 에 의존하므로
구조적으로 환경에 민감하고, 2차 실행 때 한 번 난 실패는 **그 당시 서버 부하**(T-148 세션의 jest·운영 pm2 앱 동시 가동) 외에
다른 설명을 찾지 못했다. **원인을 호스트 부하로 단정하지 않는다 — 모른다.** 재발하면 이 수치와 비교할 수 있도록 남긴다.

|---|---|---|---|---|
| 실제 러너 | ok | ok | **ok** | PASS=105 FAIL=1 |
| 변이판(가드 제거) | ok | ok | **FAIL (기대 0, 실제 1)** | PASS=101 FAIL=5 |
