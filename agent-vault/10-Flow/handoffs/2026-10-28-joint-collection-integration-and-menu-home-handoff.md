## 0. 이 문서의 용도

두 세션이 **같은 저장소·같은 DB·같은 크론 파일**을 서로 모른 채 건드리지 않도록 ① 각자의 현재 상태 ② 만나는 지점과 합의 제안 ③ 파일 소유권 ④ 순서·의존성 ⑤ 사용자 결정 대기 ⑥ 첫 행동을 한곳에 둔다. 표기: **[확실]** 문서·소스를 직접 읽음 · **[제안]** 상대 세션 확인 전의 합의안(확정 아님) · **[추측]** 추정. 합의 결과는 §11 조율 로그에 한 줄씩 **추가만** 한다(남의 줄 수정 금지).

세션 이름: **T-108 세션** = 메뉴·홈 개편 + 분석 기록 기반 + 비서 소유권 설계 / **수집 통합 세션** = T-111 2차 설계(기업정보 통합).

## 2. 불편한 사실 (먼저)

1. **같은 "작업 상태·실행 기록"을 세 곳이 따로 만들려 한다 [확실].** T-104(범위 C)는 "오늘 미실행 / 마지막 실행 + N분" 판정 상태가 필요하고, T-108 은 "예정 회차 대비 정상 회차"(가동률)를 홈에 보여야 하며, T-111 은 "원천별 최초/마지막 성공·실패·건수·지연, 날짜파일=성공 아님"(1차 설계 §4 운영 행, §5.3)을 정한다. 지금은 날짜 파일·로컬 하트비트 파일·pm2 로그뿐이고 DB 에는 잡 실행 기록이 없다 [조사]. 따로 만들면 테이블 3개·기준 3개가 되고 홈 숫자가 서로 어긋난다 → **§4 J1 로 하나로 만든다.**
2. **4주 관찰의 기준선이 관찰 중에 움직이고 있다 [확실].** 관찰 증거(후보·제외 추이, 사후 성과, 가동률)는 "분석 파이프라인이 그대로"여야 의미가 있는데, 10-28 하루에만 해외 분석 스위치 ON·뉴스 수집 국내/해외 분리·M4 날짜 정규화가 들어갔고, T-104 주기 변경·T-105 후속·T-109 연결·T-111 구현이 더 예정돼 있다. 막을 수는 없지만 **효과 시각을 대장에 남기지 않으면 11-23 에 전/후를 나눌 수 없다** → §10 대장.
3. **같은 파일을 최대 4개 task 가 건드린다 [확실].** `src/app/api/cron/*` 8개 라우트(T-104 WP2 게이트), `scripts/cron-runner.sh`(T-104 WP3·이후 기록·Fast Watch 격리), `src/lib/strategy/post-market-*`(기록·사건 참고 판단). 이 경로는 커밋 훅 `SAFETY_PATHS` 대상이라 Reviewer 판정 scope 가 얽힌다 → §6 소유권 + J1 의 "기록 지점 1곳".
4. **속도가 비대칭이다.** T-108 쪽은 "기록을 UI 보다 먼저, 빨리 시작"(4주 관찰 시계가 이미 돌고 있음), 수집 통합은 "2차 설계 전 구현 금지". 새 기록 테이블을 먼저 만들면 2차 설계의 상태 모델과 갈라질 수 있다 → §4 J1 의 **호환 최소 스키마 + 사전 확인 게이트**. **[17:09 갱신]** 사용자 지시 D-1 로 T-108 착수가 2차 설계 완료 뒤로 이동해 기록 시작도 그만큼 늦어진다 — 하루 늦을 때마다 11-23 까지 쌓일 기록이 하루 줄어든다 [확실, 산술]. 완화안은 U7(2차 설계 안에서 J1 상태 모델만 먼저 확정).
5. **task 번호가 이미 충돌했다 [확실].** T-108 세션이 계획에서 예약했던 T-111 은 수집 통합이 먼저 `T-111-corporate-intelligence-first-design` 으로 사용했다(vault 에 흔적 없는 로컬 계획 파일만의 예약이라 막지 못함). 다음 번호는 §3 규칙으로 잡는다.
6. **수집 통합 쪽 1차 설계에도 T-108 이 모르는 전제가 있다.** "일일 수집만으로는 분 단위 최초 탐지 불가, Fast Watch 는 추가 경로", "저장되지 않은 옛 RSS 원문·덮어쓴 SEC 값은 소급 복원 불가" 등 [확실, 1차 설계 §1·§5.6]. 홈이 "사건 정보가 있다"를 암시하는 문구를 쓰면 안 된다 → J5.
