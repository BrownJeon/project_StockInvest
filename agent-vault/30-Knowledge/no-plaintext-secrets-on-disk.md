# 🔴 복호화된 비밀정보를 디스크에 쓰지 않는다 (절대)

## 규칙

**복호화·평문 상태의 비밀정보(KIS App Key/Secret/계좌번호, `AUTH_SESSION_SECRET`, `CREDENTIALS_ENCRYPTION_KEY`, `SMTP_PASS`, 초대코드 등)를 어떤 이유로도 파일로 쓰지 않는다.**

검증이 필요하면 다음 중 하나만 쓴다:

| 방법 | 용도 |
|---|---|
| **한 프로세스 안에서 메모리 비교** | 로그 스캔, 값 일치 확인 — 프로세스를 나누지 않으면 파일이 필요 없다 |
| **해시 비교** (SHA-256 접두사) | 두 저장소의 값이 같은지 확인. 이 프로젝트에서 `cred_*` vs `.env` 대조에 이미 사용 |
| **마스킹된 값** | 로그·보고서 표기 (`46****16`) |
| **길이·존재 여부만** | "설정됐는가" 확인 |

## 위반 사례 — 2026-08-09, T-011 배포 검증 중 (Leader)

배포 후 "부팅 로그에 평문이 노출됐는지" 확인하려고, `system_config.cred_*` 에서 **KIS App Key·App Secret·계좌번호를 복호화해 `/tmp/t011-secrets.json` 에 평문 JSON 으로 기록**했다. 다음 명령에서 읽고 `rm` 했다.

### 왜 그랬나 (원인 — 변명이 아니라 재발 방지용 기록)

**Bash 호출을 두 번으로 쪼갰기 때문이다.** DB 조회가 한 명령, 로그 스캔이 다음 명령이었고, **명령마다 프로세스가 다르므로 메모리 상태가 이어지지 않는다.** 값을 넘기려고 임시파일을 썼다.

즉 **보안 판단이 아니라 도구 사용상의 편의**였고, 그래서 더 위험하다 — 원칙을 부정한 게 아니라 **원칙이 적용되는 상황임을 인지하지 못한 채** 손이 먼저 나갔다. 같은 task 안에서 이미 SHA-256 비교를 썼으면서도, 문제의 모양이 바뀌자 적용하지 못했다.

**올바른 해법은 자명했다: 두 작업을 한 스크립트에 합치면 비밀값이 프로세스 메모리를 벗어나지 않는다.**

### 노출 평가 (실측)

| 항목 | 실측 |
|---|---|
| 파일 권한 | **664 (rw-rw-r--) = 월드 리더블** — umask 0002, `fs.writeFileSync` 기본값 |
| 위치 | `/tmp` — 권한 `1777`, 항목 2,145개, **공용 디렉토리** |
| 파일시스템 | `/dev/nvme0n1p2` **ext4 (디스크)** — tmpfs 아님. 재부팅으로 사라지지 않음 |
| 노출 창 | 연속된 두 명령 사이, **수초~1분** |
| 동시 로그인 사용자 | 2명 |
| 백업 대상 | **아님** — rsnapshot/borg/restic/duplicity 없음, 백업 cron 없음 → **외부 사본 없음** |
| 현재 잔존 | **없음** (`ls` 확인, `/tmp` 내 `*secret*`·`*t011*` 잔여 0) |

**잔여 위험**: ext4 는 secure delete 를 하지 않으므로 해당 블록이 덮어써지기 전까지 **디스크 레벨에서 복구 가능성이 이론적으로 남는다**(root/디스크 접근 권한 필요). 백업 사본은 없다.

## 재발 방지 체크

비밀정보를 다루는 명령을 쓰기 전에 스스로 묻는다:

1. **이 값이 프로세스 메모리를 벗어나는가?** (파일·환경변수·인자·로그) → 벗어나면 멈춘다
2. **여러 Bash 호출로 쪼개고 있는가?** → 쪼개면 값을 넘길 방법이 필요해지고, 그 순간 파일에 손이 간다. **한 스크립트로 합쳐라**
3. **비교가 목적인가?** → 해시로 충분하다. 원문 대조가 정말 필요한 경우는 거의 없다
4. `rm` 으로 지울 계획이라면 **애초에 쓰지 말았어야 한다** — 삭제는 노출을 되돌리지 못한다
