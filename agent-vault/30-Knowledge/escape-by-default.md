# 열거해서 막지 말고, 무조건 이스케이프하라

## 사례 (T-010, 2026-08-09)

사용자 입력이 알림 본문에 들어가 텔레그램(`parse_mode:'HTML'`)·슬랙(mrkdwn) 양쪽으로 나가는 경로가 있었다. 이 경로의 위험도를 두 사람이 **각자 열거**했고, **둘 다 틀렸다**:

| 판단자 | 결론 | 실제 |
|---|---|---|
| reviewer | "`<a href=...>` 는 attribute 에 **공백**이 필요한데 `isValidEmail` 이 공백을 막으니 클릭형 링크 불가" | ❌ **슬랙 링크 문법 `<url\|text>` 은 공백이 필요 없다** |
| developer | "깨진 HTML 로 텔레그램 400 → 전달 실패 벡터일 뿐" | ❌ 슬랙에선 정상 렌더되는 **피싱 링크** |

실측: `ab@<https://evil.com|ClickHere>` 가 `isValidEmail` **통과** → `maskEmail` 거쳐 `ab*@<https://evil.com|ClickHere>` 로 알림에 삽입.

## 그런데 T-010 은 안전했다 — 이유가 중요하다

수정 당시 **어떤 페이로드가 도달 가능한지 열거하지 않고**, 주입 지점에서 `<` `>` `&` 를 **무조건 이스케이프**했다. 그래서 **이 벡터의 존재를 아무도 몰랐던 시점부터 이미 막혀 있었다.**

> **열거해서 막는 방식은 열거가 완전해야만 안전하다. 무조건 이스케이프는 열거가 틀려도 안전하다.**

이번엔 감사자와 구현자가 **둘 다** 열거에 실패했는데도 결과가 안전했다. 열거에 의존했다면 취약했을 것이다.

## 적용 규칙

1. **렌더러(HTML·mrkdwn·마크다운)로 들어가는 사용자 입력은 주입 지점에서 무조건 이스케이프한다.** "이 필드는 검증되니까 괜찮다"는 논증을 신뢰하지 않는다 — 검증 규칙과 렌더러 문법은 **서로 모르는 사이**다.
2. **한 본문이 여러 채널로 팬아웃되면**(`dispatchAlert` → 텔레그램+슬랙) 이스케이프는 **모든 채널 문법의 교집합**이어야 한다. `&` `<` `>` 가 그 교집합이다.
3. **채널별 포맷 변환 함수를 통째로 재사용하지 말 것.** `mrkdwnToTelegramHtml` 은 이스케이프 + `*굵게*`→`<b>` 변환을 겸하는데, 이걸 슬랙 본문에 쓰면 `<b>` 가 슬랙에선 **링크 문법**이라 구멍이 반대편에서 다시 열린다. 이스케이프 부분만 분리한 `escapeAlertText()` 가 채널 중립 부분이다.
4. **검증 함수는 렌더러 안전성을 보장하지 않는다.** `isValidEmail` 은 이메일 형식만 본다 — `<`, `|`, `>` 가 통과하는 것은 이메일 규격상 버그가 아니다.

## 부수 교훈 — 감사 근거도 실측으로 검증하라

reviewer 의 심각도 판정이 **틀린 전제** 위에 있었고, 그대로 두면 백로그 티켓이 잘못된 근거로 낮게 분류될 뻔했다. developer 가 페이로드를 **직접 실행**해 정정했다. 판정의 **근거**가 실측인지 추론인지 구분할 것.
